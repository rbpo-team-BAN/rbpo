# Паспорт проекта

## Общие сведения

Название команды: БАН

Название продукта: ConfigRelease

Коды участников: `M1`, `M2`, `M3`

Статус ранней калибровки: `черновик`

Основа: тема №24 «Публикация конфигураций приложений» из банка идей курса.

Модификация темы: загрузка YAML-файла, отдельное рассмотрение перед публикацией и получение конфигурации сервисным клиентом. Статус калибровки обновляется после обратной связи преподавателя.

## 1. Назначение

ConfigRelease управляет выпуском конфигураций учебных приложений в окружения `dev` и `prod`. Редактор загружает версию, публикатор рассматривает и выпускает её, приложение-потребитель получает текущую опубликованную конфигурацию своей пары «приложение + окружение».

Собственная предметная логика: проверка конфигурации, жизненный цикл версии, отдельное одобрение, выбор текущей публикации и история решений и выпусков.

## 2. Граница продукта

В продукт входит:

- серверный HTTP API для загрузки, просмотра, рассмотрения и публикации версий;
- проверка YAML-файла и его значений;
- определение человека или сервисного клиента по токену и проверка его доступа;
- постоянное хранилище приложений, окружений, версий, решений, публикаций и назначений;
- выдача текущей опубликованной конфигурации сервисному клиенту;
- история решений и выпусков с исполнителем и временем.

Внешнее окружение и внешние системы:

- HTTP-клиенты людей: `curl`, PowerShell или Postman;
- приложения-потребители; для демонстрации достаточно HTTP-запроса с сервисным токеном;
- локальная машина, .NET SDK и файловая система для SQLite.

Внешние сервисы для работы продукта не нужны. Отдельное приложение-потребитель команда не разрабатывает.

Команда сознательно не реализует в обязательном ядре:

- полноценный веб-интерфейс, мобильный клиент, уведомления и реальные интеграции;
- регистрацию, SSO, API администрирования и универсальный редактор схем;
- редактирование загруженного содержимого, наследование и слияние конфигураций;
- форматы, кроме YAML;
- просмотр различий, отзыв с рассмотрения, откат и повторную публикацию выпущенной версии;
- маскирование значений и шифрование отдельных полей;
- исполнение конфигурации или обращения по адресам из её содержимого.

Используются только учебные значения. Реальные конфигурации, персональные данные и действующие внешние секреты в проект не входят.

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| Редактор | Учебный пользователь, назначенный на приложение | Просматривать версии и историю назначенного приложения; загружать версии для его окружений; отправлять собственный черновик на рассмотрение | Читать чужие приложения; менять содержимое загруженной версии; одобрять и публиковать без отдельного назначения публикатора |
| Публикатор | Пользователь, назначенный на пару «приложение + окружение» | Просматривать версии и историю своей пары; одобрять или отклонять версии на рассмотрении; публиковать одобренную версию своей пары | Изменять содержимое; работать с чужими парами; одобрять собственную загрузку |
| Приложение-потребитель | Машинный клиент с сервисным токеном для одной пары | Получать текущую опубликованную конфигурацию своей пары | Читать черновики, решения, историю и другие пары; изменять данные |
| Посетитель без токена | Любой HTTP-клиент | Проверять работу через `GET /health` | Получать конфигурации и выполнять предметные операции |

Учётные записи, приложения, окружения, схемы и назначения задаются начальными данными; роли администратора нет. Для последующих проверок предусматриваются два учебных приложения, у каждого — `dev` и `prod`.

Планируемый вход — по индивидуальным непрозрачным Bearer-токенам людей и отдельным сервисным токенам. Сервер определяет субъект и назначения по токену, а не по переданным клиентом имени пользователя или роли. Локальные токены настраиваются вне отслеживаемых файлов репозитория.

Человек может совмещать назначения. Запрет одобрять свою версию сохраняется и при совмещении ролей. После одобрения другим человеком автор может выпустить её, если назначен публикатором целевой пары.

## 4. Сквозные сценарии

### Сценарий 1. Подготовить конфигурацию к рассмотрению

- Участники: редактор.
- Начальное условие: приложение и окружение существуют, редактор назначен на приложение.
- Основные действия: редактор выбирает приложение и окружение, загружает YAML; сервер проверяет файл и сохраняет черновик; редактор отправляет собственный черновик на рассмотрение.
- Результат: версия ожидает решения публикатора для выбранного окружения.
- Какие данные или состояние изменяются: создаётся версия с автором и содержимым; статус меняется с `draft` на `in_review`; фиксируется отправка на рассмотрение.

При недопустимом файле версия не создаётся. Исправление содержимого оформляется новой загрузкой.

### Сценарий 2. Рассмотреть и выпустить конфигурацию

- Участники: публикатор и приложение-потребитель; при отклонении — редактор.
- Начальное условие: есть версия `in_review` для пары публикатора, загруженная другим человеком.
- Основные действия: публикатор просматривает содержимое и одобряет версию либо отклоняет с причиной. Одобрение и публикация — разные операции. Одобренная версия выпускается публикатором; сервисный клиент запрашивает текущую конфигурацию.
- Результат: потребитель получает одобренное содержимое либо редактор видит причину отказа и готовит новую версию.
- Какие данные или состояние изменяются: статус и решение с исполнителем и временем; при выпуске — текущая публикация пары и история выпусков.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Содержимое конфигураций | Редактор, публикатор, потребитель | Посторонний узнаёт внутренние настройки и ещё не согласованные параметры | Потребитель получает неверный таймаут, уровень журналирования или состояние функции; отсутствие версии мешает выпуску |
| Текущая публикация пары | Публикатор и потребитель | Посторонний узнаёт, какие настройки используются в окружении | Потребитель работает с чужой или неодобренной конфигурацией либо не получает настройки |
| Решения и история выпусков | Редактор и публикатор | Раскрываются действия пользователей и причины отказов | Нельзя установить исполнителя; история расходится с текущей публикацией |
| Учётные записи, назначения и токены | Все субъекты | С чужим токеном можно действовать от имени его владельца | Подмена назначений предоставляет лишние права; удаление лишает законного субъекта доступа |
| Схема приложения | Редактор и публикатор | Сама схема секретов не содержит | Недопустимые значения проходят проверку либо корректные версии невозможно загрузить |

## 6. Компоненты и внешние взаимодействия

Планируемая архитектура:

```text
Редактор / публикатор
  ── токен, YAML-файл, идентификаторы и команды ──> ConfigRelease API
  <── версии, состояния, решения и история ─────── ConfigRelease API

Приложение-потребитель
  ── сервисный токен, запрос текущей версии ─────> ConfigRelease API
  <── опубликованная конфигурация своей пары ──── ConfigRelease API

ConfigRelease API
  <── приложения, назначения, версии, решения и публикации ──> SQLite
```

В сервере планируются обработчики API, определение субъекта, проверка доступа, обработка YAML и операции над состоянием. Фоновые процессы и отдельные микросервисы не нужны.

Что уже существует: ASP.NET Core API с `GET /health` и локальным запуском; исходный код — `src/ConfigRelease.Api`.

Что пока планируется: SQLite, начальные данные, токены, обработка YAML и предметные операции. Эти части в текущей основе не реализованы.

Локальная демонстрация работает на loopback-адресе. Публичное развёртывание в текущую основу не входит. Начальные данные и локальные настройки контролирует команда; HTTP-клиенты напрямую хранилищем не управляют.

## 7. Откуда продукт получает данные

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| Загружаемый файл | YAML с настройками приложения | Редактор | Проверяет и сохраняет неизменяемую версию |
| Параметры HTTP-запроса | ID приложения, окружения и версии | Клиент | Находит объект и проверяет допустимость действия |
| Тело команды | Причина отклонения | Публикатор | Сохраняет решение и показывает редактору |
| Заголовок `Authorization` | Индивидуальный или сервисный токен | Клиент | Определяет субъект и назначения |
| Начальные данные и локальные настройки | Приложения, окружения, схемы, учётные записи и назначения | Команда | Создаёт учебное окружение и задаёт структуру конфигураций |
| Текущее серверное состояние | Автор, статус, текущая публикация | Сервер | Проверяет переходы и формирует результат операции |

## 8. Минимальное функциональное ядро

Обязательные функции продукта:

- загрузка версии с проверкой YAML;
- просмотр доступных версий и их состояния;
- отправка собственного черновика на рассмотрение;
- одобрение либо отклонение с непустой причиной;
- отдельная публикация одобренной версии;
- чтение текущей конфигурации сервисным клиентом;
- проверка доступа по субъекту, действию, приложению и окружению;
- сохранение и просмотр доступной истории с исполнителями и временем.

Правила ядра:

1. Версия закрепляется за одной парой «приложение + окружение». Её содержимое, автор и пара после загрузки неизменны. Для другого окружения даже одинаковый файл загружается как новая версия.
2. Допустимые переходы: `draft → in_review → approved → published` или `in_review → rejected`. Отклонённая версия остаётся в истории; исправление — новая загрузка. Отзыв и повторная публикация отсутствуют.
3. Одобрение относится к содержимому и паре конкретной версии. Одобрение для `dev` не разрешает выпуск в `prod`.
4. Автор не одобряет собственную версию. Выпуск доступен публикатору целевой пары только для версии `approved`.
5. Для пары существует не более одной текущей публикации. Прежняя версия сохраняет статус `published`, но перестаёт быть текущей. Успешный выпуск согласованно сохраняет статус, текущую публикацию и историю.
6. Потребитель получает конфигурацию только своей пары. При отсутствии публикаций сервер сообщает об этом без выдачи черновика или конфигурации другого окружения.
7. Допустимый файл — один UTF-8 YAML-документ размером не более 16 КиБ, плоский набор трёх обязательных полей: `logLevel` (`Debug`, `Information`, `Warning` или `Error`), `requestTimeoutSeconds` (целое число 1–120), `featureEnabled` (логическое значение). Другие и повторяющиеся поля, вложенные структуры, алиасы и пользовательские теги не допускаются.
8. Схема задаётся начальными данными для приложения и не меняется через API. В ядре оба учебных приложения используют описанную структуру; универсальный механизм произвольных схем не требуется.

Функции, которые можно добавить после завершения ядра: просмотр различий, отзыв с рассмотрения и откат. Они не являются обещанными сценариями этого паспорта и не нужны для технической основы ЕК1.

## 9. Стек и путь к первой работающей версии

Основные технологии: C#, .NET 10, ASP.NET Core Web API. Для последующей реализации — EF Core и SQLite, YamlDotNet; для проверок — xUnit и `WebApplicationFactory`. Swagger UI можно добавить как удобный клиент, но он не обязателен.

Технологии, новые для команды: предыдущий опыт участников не заявлен. В проекте потребуется освоить или закрепить ASP.NET Core, EF Core с SQLite, обработку YAML и интеграционные проверки. Персональный уровень владения этими технологиями не является допущением для запуска текущей основы.

Внешние сервисы, необходимые для запуска: отсутствуют. Текущий API использует ASP.NET Core из SDK без сторонних NuGet-пакетов.

Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов: локальный API, SQLite, начальные данные и HTTP-запросы от имени разных субъектов. Потребители заменяются запросами с сервисными токенами. После добавления библиотек их первоначальное восстановление потребует источника пакетов или локального кеша.

Первый технический результат — выполнен: Web API с `GET /health`, сборкой и инструкцией запуска. Следующие шаги реализации — хранилище, начальные данные и операции ядра. Полная реализация сценариев к ЕК1 не заявляется.

## 10. Локальный запуск

Требования к окружению: стабильный .NET SDK 10; Windows с PowerShell либо Linux/macOS с терминалом. Выбор SDK описан в `global.json`. База данных и внешние сервисы для текущей основы не нужны.

Команды установки, сборки и запуска: приведены в [README.md](README.md#локальный-запуск), включая использование локальной папки `.dotnet`.

Запрос для проверки:

```text
GET http://127.0.0.1:5080/health
```

Ожидаемый результат: HTTP `200 OK`, `Content-Type: application/json`, тело:

```json
{"status":"ok","service":"ConfigRelease"}
```

Это подтверждение запуска технической основы. Предметные операции, хранилище и защитные механизмы пока планируются; `/health` не подтверждает их выполнение.
