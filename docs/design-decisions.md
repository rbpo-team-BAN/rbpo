# Проектные решения безопасности ConfigRelease

Решения опираются на [паспорт](../PROJECT.md), [требования SR](security-requirements.md) и [модель угроз T](threat-model.md). Пара (C, E), предложения и операции O1–O10 понимаются так же, как в SR.

**Состояние:** все три решения планируются. Сейчас реализован только `GET /health`; аутентификации, базы, проверки YAML и предметных операций ещё нет. Проверки ниже — планы, а не выполненные тесты. ID вида `D-02-P3` обозначают отдельные будущие проверки.

## Решения

### D-01. Субъект и полномочия определяются сервером

**Контекст:** имя, роль, конфигурация и окружение в запросе управляются клиентом. Апрув сразу выпускает настройки, а учётные данные потребителя должны давать доступ только к одной текущей публикации. Назначения апруверов могут измениться после отправки предложения.

**Решение:**

1. При подготовке учебного окружения сервер генерирует для каждого человека и каждого сервисного клиента свой случайный токен. Клиент передаёт его в заголовке `Authorization: Bearer <токен>`. Значение выбирает сервер, ID или роли внутри токена нет.
2. В базе хранится не сам токен, а его хеш и связь с субъектом: ID, вид (человек или сервисный клиент) и признак действительности. Исходные токены выдаются владельцам и хранятся только в локальном файле вне Git; в ответах и журналах они не выводятся. Начальные назначения, схемы и учётные записи задаются доверенной настройкой на компьютере команды. Публичного API регистрации и выдачи полномочий нет.
3. Компонент аутентификации сопоставляет предъявленный токен с серверной записью и устанавливает ID и вид субъекта. Имена, роли и указания исполнителя в параметрах или заголовках эту запись не заменяют. Автор предложения и исполнитель в истории берутся из установленного ID. Неверный формат тела проверяется отдельно по D-03.
4. Перед каждой O1–O10 сервер проверяет текущее назначение в базе по таблице операций SR. Права не записываются в токен и не копируются из времени отправки предложения. Для O5 и O6 конфигурация, окружение, автор и статус берутся из сохранённого предложения; дополнительные значения в команде их не заменяют. Если маршрут тоже содержит пару, она должна совпадать с сохранённой.
5. При O5 для prod апрувер не должен быть автором предложения. Для O6 такого запрета нет. Роль администратора не заменяет назначения редактора и апрувера. Изменение списка O8 доступно только администратору и только для существующих пользователей.
6. O10 разрешена только сервисному клиенту и только для назначенной ему пары. Запрос читает её текущий указатель и возвращает полный YAML без метаданных предложений и истории. O1–O9 доступны только людям. Обработчика, который выдаёт сервисному клиенту старую версию по переданному номеру, нет.
7. O1–O3 выбирают объекты с ограничением по разрешённой паре; право на конфигурацию не даёт доступа к любому ID предложения или версии. Чтобы права и данные не разошлись, при чтении сервер проверяет назначение и читает данные в одной транзакции. При изменении это делается внутри транзакции D-02.

**Обоснование:** случайного токена достаточно для локального учебного API, выдавать подписанные токены с ролями внутри не нужно. Права читаются из базы при каждой операции, поэтому удаление апрувера действует сразу, без перевыпуска его токена.

**Связанные угрозы:** [T-01](threat-model.md#t-01-подмена-исполнителя-через-поле-запроса), [T-02](threat-model.md#t-02-доступ-к-чужому-объекту-по-id), [T-03](threat-model.md#t-03-самоапрув-в-prod), [T-04](threat-model.md#t-04-изменение-списка-апруверов-без-прав-администратора), [T-05](threat-model.md#t-05-подмена-окружения-в-запросе-апрува), [T-08](threat-model.md#t-08-утёкший-токен-потребителя-читает-чужое-окружение), [T-09](threat-model.md#t-09-решение-апрувера-после-исключения-из-списка).

**Связанные требования:** [SR-01](security-requirements.md#sr-01-действие-выполняется-от-имени-аутентифицированного-пользователя), [SR-02](security-requirements.md#sr-02-данные-конфигурации-доступны-только-по-назначениям), [SR-03](security-requirements.md#sr-03-решение-по-предложению-принимает-только-уполномоченный-для-окружения), [SR-04](security-requirements.md#sr-04-нельзя-одобрить-собственное-предложение-в-prod), [SR-05](security-requirements.md#sr-05-отправленное-предложение-и-опубликованная-версия-не-меняются), [SR-08](security-requirements.md#sr-08-сервисный-клиент-получает-только-текущую-конфигурацию-своей-пары), [SR-09](security-requirements.md#sr-09-списки-апруверов-prod-видит-и-меняет-только-администратор), [SR-10](security-requirements.md#sr-10-действия-прослеживаются-история-не-стирается).

**Будущая проверка:**

#### D-01-P1. Идентичность и отсутствие входа

- **Ситуация:** есть пользователи A и B с разными назначениями; снят снимок предметного состояния.
- **Действие:** вызвать O1–O10 без учётных данных, с пустыми и неизвестными; отдельно вызвать `/health`. Для каждой O4, O5, O6, O8 с действительными данными A передать заголовок или параметр исполнителя B в допустимом запросе, затем повторить с A без права на операцию.
- **Результат:** недействительные данные дают отказ без изменения состояния; `/health` доступен. Разрешённая операция записывает A как автора или исполнителя, запрещённая отклоняется независимо от указания B. Критерии: SR-01.

#### D-01-P2. Чужой объект

- **Ситуация:** две конфигурации C и D, оба окружения; A — редактор C; X — апрувер prod C без назначения редактора C.
- **Действие:** под данными A запросить версию и предложение D по ID, также через маршрут с конфигурацией C, и попробовать одобрить предложение D. Под данными X запросить версии dev C.
- **Результат:** все запросы отклоняются, данные D и dev C не возвращаются, предметное состояние не меняется. Критерии: SR-02, SR-03.

#### D-01-P3. Самоапрув prod

- **Ситуация:** A — редактор C и апрувер prod C, у него есть свои предложения в prod и dev в статусе `in_review`. Администратор B назначен редактором C и добавил себя в апруверы prod C; у него есть своё предложение prod, и есть предложение prod другого редактора.
- **Действие:** A одобряет своё предложение prod, затем отклоняет его; A одобряет своё предложение dev. B одобряет своё предложение prod, затем предложение другого редактора.
- **Результат:** самоапрув prod отклоняется и у A, и у B. Самоотклонение prod и самоапрув dev проходят. B одобряет предложение другого редактора. Критерии: SR-03, SR-04.

#### D-01-P4. Права администратора

- **Ситуация:** A — редактор и апрувер prod C, но не администратор; B — администратор без назначений редактора и апрувера C.
- **Действие:** A вызывает O7–O9. B запрашивает настройки C, затем просматривает списки апруверов и их историю и меняет список апруверов C.
- **Результат:** A получает отказ на O7–O9. B не получает настройки C, но видит списки и историю и меняет список; изменение и его исполнитель видны в истории. Критерии: SR-02, SR-09.

#### D-01-P5. Отзыв права апрувера

- **Ситуация:** A — апрувер prod C, он прочитал чужое предложение prod в статусе `in_review`. Администратор завершил O8 и удалил A из апруверов C.
- **Действие:** с прежними действительными учётными данными A вызвать O5 и O6 для этого предложения.
- **Результат:** оба запроса отклоняются; прежние решения A и публикации сохраняются. Критерии: SR-03, SR-09; одновременный порядок проверяет D-02-P6.

#### D-01-P6. Потребитель

- **Ситуация:** сервисный клиент назначен только паре (C, dev); у человека есть права редактора C.
- **Действие:** клиенту вызвать O10 своей пары, O10 для (C, prod) и другой конфигурации, а также O1–O9; человеку вызвать O10.
- **Результат:** только первый запрос возвращает текущий полный YAML без служебных данных; остальные отклоняются без изменения предметного состояния. Критерии: SR-08.

**Ограничения и последствия:**

- Токен подтверждает только то, что запрос пришёл с этим токеном. Если его украдут, вор получит права владельца.
- Администратору мы доверяем: он может назначить себя апрувером и получить доступ к prod. То же с базой и локальной настройкой: кто ими управляет, тот управляет правами.
- Редакторы, доступ сервисных клиентов и администраторы меняются вне API, через начальные данные. Удаление из апруверов не отзывает остальные права пользователя.
- HTTP без шифрования подходит только для локального запуска на 127.0.0.1. Для удалённого размещения нужны HTTPS и пересмотр того, как выдаются, хранятся и отзываются токены.

### D-02. Команды меняют состояние и историю атомарно

**Контекст:** два апрува могут одновременно прочитать одну текущую версию. Проверка только прежнего значения не обнаруживает изменение поля и возврат обратно. Отдельная запись публикации и истории оставляет неполный результат при сбое. Удаление апрувера между проверкой прав и записью тоже меняет допустимость действия.

**Решение:**

1. Хранить предложения, полные версии, текущие указатели, отметки изменения полей, назначения и историю в одной SQLite-базе. O4, O5, O6 и O8 выполняются как отдельные команды, каждая в одной транзакции. Транзакция занимает право записи сразу, ещё до чтения назначений и состояния, поэтому пока одна команда работает, другие изменяющие команды ждут. Все записи команды идут только через эту транзакцию.
2. В транзакции заново прочитать действительность учётных данных, текущие назначения и целевой объект. Для O5 и O6 проверить сохранённые пару, автора и `in_review`; для O8 — администратора и существование назначаемого пользователя. Проверки вне транзакции могут дать ранний отказ, но не заменяют окончательные.
3. При O4 сохранить проверенные базовую версию, изменения, автора и пару как неизменяемые данные. Создать только `in_review` и запись истории. Универсальных операций изменения или удаления предложений, версий и истории нет.
4. Для каждого поля пары хранить номер версии, в которой значение последний раз изменилось. Начальная опубликованная версия и её отметки задаются при подготовке данных. При O5 каждое затронутое поле не должно было меняться после базовой версии (`lastChangedVersion <= baseVersion`). Значение `old` ранее сверяется с полной базовой версией. Сравнения текущего значения с `old` для поиска конфликта недостаточно.
5. Прочитать текущую полную конфигурацию и применить к ней только сохранённые изменения. Проверить весь результат по схеме и размер итогового YAML: не более 16 384 байт по D-03. Невнесённые в предложение поля сохранить из текущей публикации, а не из базовой версии.
6. При успехе назначить номер на единицу больше текущего, сохранить полную версию, обновить отметки изменённых полей и единственный текущий указатель пары, перевести предложение в `applied`, записать решение и одну запись истории. Все изменения входят в одну транзакцию. Номер версии уникален в пределах пары — это обеспечивает ограничение уникальности в базе; у пары одна запись текущего указателя.
7. Для O6 статус `rejected`, непустая причина и история сохраняются совместно. Для O8 совместно сохраняются назначение и история. Исполнитель определяется по D-01, время — сервером. При отказе или ошибке до успешного commit выполняется rollback всей команды, и записи истории о выполненном действии не появляется. Отказы можно писать в технический журнал без секретов, но это не история выполненных действий.
8. Второй запрос ждёт, пока первый закончит, и затем читает уже новое состояние. Время ожидания ограничено; если оно вышло, сервер отвечает, что база занята, и ничего не меняет. Повторять можно только всю команду целиком, заново прочитав права и состояние.

**Обоснование и сравнение альтернатив:**

| Способ | Что обеспечивает | Компромисс для ConfigRelease |
| --- | --- | --- |
| Сразу занять право записи, потом читать и проверять (`BEGIN IMMEDIATE` в SQLite) — выбранный способ | Все проверки и изменения команды выполняются, когда право записи уже получено; другой писатель не меняет проверяемое состояние до конца команды | Порядок проверки прав и публикации простой; право записи занято и во время проверок, даже если команда в итоге отклонится |
| Сначала читать, а право записи брать только в момент записи (`BEGIN DEFERRED`); если за это время данные изменились, повторить команду целиком | Те же отметки полей и проверка результата; при устаревших данных транзакция отменяется, и новая попытка заново читает учётные данные, назначения и состояние | Пока команда читает, право записи свободно. Зато возможны повторные чтения и проверки, и нужен ограниченный повтор всей команды целиком |

В обоих вариантах остаются один писатель, отметки отдельных полей, проверка полной конфигурации и совместная запись состояния и истории, поэтому правила SR-06 соблюдаются. Во втором варианте, если другая команда успела записать данные, транзакцию нужно отменить и начать команду заново, с ограниченным числом попыток. Старое разрешение апрувера нельзя переносить в новую попытку: O8 мог удалить назначение.

Выбираем первый способ. Команды короткие, и простой порядок «проверить права — опубликовать — записать историю» для нас важнее, чем время, на которое занято право записи. Выбор стоит пересмотреть, если замеры покажут, что проверки внутри команд заметно задерживают другие записи, а ограниченные повторы второго варианта работают без потери актуальности прав. D-02-P6 проверяет порядок отзыва прав, D-02-P7 — риск устаревших данных во втором варианте.

**Пограничный случай.** Сначала мы считали, что два предложения, которые меняют разные поля, можно спокойно применить оба: конфликта по отметкам нет. Это неверно, если в схеме есть связь между полями. Пример: `min = 1`, `max = 10`, схема требует `min <= max`. Предложение A меняет `min` на 8, предложение B меняет `max` на 5. Каждое по отдельности проходит проверку, а вместе они дают `min = 8`, `max = 5`. Что мы изменили после этого разбора:

- добавили угрозу [T-10](threat-model.md#t-10-два-корректных-предложения-вместе-нарушают-схему);
- в SR-06, пп. 5–6, оба предложения применяются, только если проходят проверку и каждый промежуточный результат, и общий;
- D-02 проверяет всю конфигурацию после каждого применения;
- проверка D-02-P4 подтверждает, что второе предложение отклоняется.

**Будущая проверка:** для каждого сценария подготовить отдельную учебную базу и сравнить через разрешённые запросы версии, текущую публикацию, статус и историю. Отметки и ограничения базы дополнительно проверить интеграционным тестом. Использовать отдельные соединения; конкурентные тесты не выполнять внутри одной общей тестовой транзакции.

#### D-02-P1. Два независимых изменения

- **Ситуация:** A и B одной пары основаны на версии N, меняют разные поля; оба промежуточных и общий результаты допустимы. Нет другой нагрузки и сбоя записи.
- **Действие:** одновременно отправить два разрешённых апрува с отдельными соединениями; согласовать начало запросов тестовым барьером.
- **Результат:** два успешных применения; версии N+1 и N+2; последняя содержит оба изменения, остальные поля сохранены. Отметки изменены только для затронутых полей; на каждое применение одна запись истории. Критерии: SR-06, пп. 1, 5–6.

#### D-02-P2. Одно поле и возврат значения

- **Ситуация:** два предложения от N меняют одно поле; отдельно подготовлен случай, где поле после N меняется и затем возвращается к исходному значению.
- **Действие:** сначала выполнить одновременные апрувы двух предложений; затем попытаться применить старое предложение в случае возврата значения.
- **Результат:** в первом случае одно применение, у второго конфликт; во втором конфликт несмотря на совпадение `old` с текущим значением. Отказ не создаёт версию, не меняет отметки и оставляет предложение в `in_review`. Критерии: SR-06, пп. 2, 4.

#### D-02-P3. Неизменяемость и повтор команды

- **Ситуация:** есть сохранённое предложение для dev, опубликованная версия и завершённое предложение.
- **Действие:** в апруве передать другое окружение, автора и изменения; попытаться изменить версию и историю; повторить апрув и отклонение завершённого предложения.
- **Результат:** метаданные команды не заменяют сохранённое предложение; без права на его действительную пару запрос отклоняется. Версия и история не меняются; повторное решение не создаёт ни версии, ни истории. Критерии: SR-05, SR-10.

#### D-02-P4. Связанные поля и размер полного результата

- **Ситуация:** схема учебной C содержит связь `min <= max`; подготовлены A и B из пограничного случая. Отдельно есть допустимые изменения, после которых полный YAML превысит 16 384 байта.
- **Действие:** одобрить A, затем B; в отдельной базе одобрить предложение с превышением размера результата.
- **Результат:** A применяется, B отклоняется по схеме и остаётся в `in_review`; результат A сохраняется. Превышение размера тоже отклоняется без публикации, изменения отметок и успешной истории. Критерии: SR-06, п. 3; ограничение размера из паспорта.

#### D-02-P5. Сбой между записями

- **Ситуация:** есть разрешённые O4, O5, O6 и O8; снимок состояния сохранён. В тестовой реализации предусмотрена управляемая ошибка до commit.
- **Действие:** по очереди вызвать ошибку после записи состояния, но до записи истории, и после записи истории до commit; закрыть соединение и открыть новое.
- **Результат:** для каждой команды предметное состояние соответствует снимку до запроса; нет частичной версии, решения, назначения или записи истории. При O5 предложение остаётся в `in_review`. Критерии: SR-06, п. 7; SR-09, SR-10.

#### D-02-P6. Удаление апрувера и одновременный апрув

- **Ситуация:** пользователь A — апрувер prod C; есть чужое предложение `in_review`.
- **Действие:** выполнить O8 удаления A и O5 в двух соединениях; отдельно управлять порядком получения права записи: сначала O8, затем O5, и наоборот.
- **Результат:** если удаление зафиксировано первым, O5 перечитывает список и отклоняется. Если O5 получил право записи первым, он завершается до удаления, его решение остаётся в истории; все последующие решения A запрещены. Нет публикации по назначению, уже удалённому в зафиксированном состоянии. Критерии: SR-03, SR-09.

#### D-02-P7. Переход от чтения к записи

Дополнительная проверка для второго варианта, если мы к нему вернёмся. Нужны два отдельных соединения с тестовой базой.

- **Ситуация:** соединение X начало транзакцию по второму варианту и прочитало разрешение пользователя A на апрув и текущее состояние; соединение Y после этого завершило O8 и удалило назначение A.
- **Действие:** через X попытаться записать результат по старым данным; после отказа базы выполнить rollback и ограниченную повторную попытку всей команды.
- **Результат:** старые данные не используются для публикации; повторная попытка читает удалённое назначение и отклоняется. Нет новой версии и записи истории об апруве. Проверка понадобится при пересмотре выбранного способа.

**Ограничения и последствия:**

- Защита работает, только пока все записи идут через этот API и одну базу. Владелец компьютера может изменить файл базы напрямую, и история этого не покажет.
- Одновременно пишет только одна команда. При большой нагрузке запрос может не дождаться своей очереди и получить ответ, что база занята.
- Если ответ на апрув потерялся после commit, публикация уже произошла. Клиент проверяет статус предложения, а повторный апрув второй раз его не применит.
- Несколько серверов, внешняя история или изменение схем через API потребуют пересмотреть решение.

### D-03. YAML разбирается ограниченно и проверяется по доверенной схеме

**Контекст:** предложение — недоверенный текст. Маленький YAML может содержать повторяющиеся ключи, ссылки или значения неожиданного типа. Проверка только изменяемого значения не гарантирует допустимость всей опубликованной конфигурации. Текст исключения может раскрыть внутреннее устройство сервера.

**Решение:**

1. До полного разбора тела ограничить фактически прочитанные байты числом 16 384. `Content-Length` использовать только для раннего отказа, а не как доказательство размера; при чтении потока прекратить обработку на превышении лимита. Принимать `application/yaml`, строго декодировать UTF-8 с отказом на недопустимых последовательностях.
2. YamlDotNet использовать как синтаксический парсер. До построения модели предложения просмотреть события: один документ, строковые уникальные ключи на каждом уровне, глубина не более 8 с корнем на первом уровне, без якорей, алиасов, ключа слияния и пользовательских тегов. Не загружать YAML непосредственно в произвольные CLR-типы по тегам и не раскрывать ссылки.
3. Разрешать только структуру `baseVersion` и непустого `changes`, внутри изменения только `old` и `new`. Изменять только существующие поля верхнего уровня со скалярными значениями. Тип каждого значения определять явно по правилам раздела 7 паспорта, с учётом кавычек и стандартных тегов. Настройкам библиотеки по умолчанию в этом не доверять.
4. Проверить тип и значение по схеме C из доверенных начальных данных. Строку `"60"` в число не преобразовывать. Стандартный тег не меняет ожидаемый тип поля. Отказывать для NaN, бесконечности и запрещённого схемой `null`. `baseVersion` должна существовать в той же паре; `old` должен совпадать со значением в базовой версии и отличаться от `new`.
5. При O5 тем же валидатором схемы проверять всю конфигурацию из D-02 вместе со связями полей; затем собрать полный YAML и проверить его размер. Строки, похожие на число или логическое значение (например, `"60"` или `"true"`), при выдаче должны остаться строками. Потребителю выдаётся заново собранный из проверенных значений YAML с явными типами, а не исходный текст предложения или версии; так потребитель с другими правилами YAML прочитает то же значение, что проверил сервер. Потребителю не передавать оболочку предложения.
6. Ошибки формата, схемы и конфликта переводить в ограниченный ответ с кодом правила и при необходимости именем поля. Не включать исходный документ целиком, стек, пути и текст исключения библиотеки. Ошибка одного предложения не завершает процесс сервера и не требует перезапуска.

**Обоснование:** лимит размера срабатывает раньше, чем сервер выделит память под весь документ. Сначала проверяем саму структуру YAML: ключи, ссылки, теги. Только потом превращаем текст в значения, поэтому повторяющиеся ключи и ссылки не попадают в данные предложения. Схема выбирается по сохранённой конфигурации и не управляется YAML клиента. Повторная проверка целого результата учитывает изменения между базовой версией и апрувом.

**Связанные угрозы:** [T-07](threat-model.md#t-07-затратный-yaml-останавливает-сервис), [T-10](threat-model.md#t-10-два-корректных-предложения-вместе-нарушают-схему), [T-11](threat-model.md#t-11-сервер-апрувер-и-потребитель-по-разному-понимают-значение).

**Связанные требования:** [SR-07](security-requirements.md#sr-07-недопустимое-предложение-отклоняется-и-не-нарушает-работу-сервиса); [SR-06](security-requirements.md#sr-06-публикуется-только-бесконфликтный-и-допустимый-результат-целиком-или-никак) — проверка результата перед публикацией.

**Будущая проверка:**

#### D-03-P1. Недопустимый ввод и продолжение работы

- **Ситуация:** редактор имеет право O4; подготовлены отдельные примеры для SR-07, пп. 1–10: поток без `Content-Length`, повтор ключа, глубина 9, алиас, неверная кодировка и другие.
- **Действие:** отправить каждый пример; затем от другого разрешённого пользователя вызвать `/health` и O1. Проверить состояние и ответ на отказ.
- **Результат:** предложение не сохранено; нет версии и успешной истории; ответ указывает правило без внутренних подробностей. Сервер без перезапуска отвечает на оба последующих запроса. Критерии: SR-07, пп. 1–11.

#### D-03-P2. Типы и граница размера

- **Ситуация:** схема требует целое `requestTimeoutSeconds` от 1 до 120 и логическое `featureEnabled`; есть допустимые `60` и `!!int 60`, недопустимые `"60"`, `!!str 60`, NaN и `null`; значения, которые YAML 1.1 и 1.2 толкуют по-разному: `requestTimeoutSeconds: 010` и `featureEnabled: yes`; подготовлены корректные документы ровно 16 384 байта и больше лимита.
- **Действие:** отправить каждый документ и проверить допустимый полный YAML после публикации; строковые значения, похожие на число или `true`, прочитать повторно по тем же правилам.
- **Результат:** допустимые документы создают предложения с правильными типами; превышение лимита и несоответствие схеме отклоняются. Размер ровно на границе сам по себе не вызывает отказа. При чтении опубликованного YAML типы и значения сохранены. `featureEnabled: yes` отклоняется как нелогическое значение. `010` принимается как 10 по YAML 1.2, и в опубликованном YAML записано `10`, поэтому разбор этого YAML по правилам YAML 1.1 тоже даёт 10. Критерии: SR-07, пп. 1, 9, 12; SR-08, п. 4; проверка целого результата — D-02-P4; угроза T-11.

**Ограничения и последствия:**

- Лимиты размера и глубины и запрет ссылок удешевляют разбор одного документа, но не спасут от потока запросов или ошибки в самом парсере.
- Поведение YamlDotNet нужно проверить на наборе примеров; проверку типов по схеме всё равно пишем сами.
- Защита публичного сервера от массовой нагрузки и выполнение правил настроек самим потребителем вне выбранного локального ядра.
