# Проектные решения безопасности ConfigRelease

Документ описывает, как ConfigRelease обеспечит требования безопасности: где принимается решение, каким данным сервер доверяет и как это будет проверено. Решения опираются на [паспорт](../PROJECT.md), [требования SR](security-requirements.md) и [модель угроз T](threat-model.md). Для каждой угрозы [приоритетного набора](threat-model.md#5-приоритетный-набор) цепочка T → SR → D → будущая проверка прослеживается по ссылкам.

**Состояние:** все решения планируются. Сейчас реализован только `GET /health`; учётных данных, базы, разбора YAML и предметных операций ещё нет. Будущие проверки - это планы, а не выполненные тесты.

## Термины

Конфигурация, предложение изменений, версия, окружение, апрув и текущая публикация понимаются так же, как в [паспорте](../PROJECT.md#термины); C, E, пара (C, E), отметка изменения поля и операции O1–O11 - как в [модели угроз](threat-model.md#термины). Буквой D в этом документе обозначаются только решения; другую конфигурацию называем словами.

- **Токен** - случайная строка, по которой сервер узнаёт пользователя или сервисного клиента (D-01).
- **Хеш токена** - результат SHA-256 от токена. Сервер хранит только его; по хешу нельзя восстановить сам токен.
- **Назначение** - запись в базе о том, что пользователь - редактор C, апрувер prod C или администратор, либо что сервисному клиенту доступна пара (C, E). Назначения описаны в [SR](security-requirements.md#термины-в-критериях-приёмки).
- **Транзакция** - группа записей в базу, которая сохраняется целиком или не сохраняется совсем (D-02).
- **Право записи** - в SQLite в каждый момент писать в базу может только одна транзакция; остальные ждут, пока она закончит (D-02).
- **Предметное состояние** - предложения, версии, текущие публикации, отметки изменения полей, списки апруверов и история, как в SR. «Предметное состояние не меняется» значит, что после запроса всё это осталось прежним.
- **Будущая проверка** - план проверки механизма решения. ID вида D-04-P2 обозначает вторую проверку решения D-04.

## Решения

### D-01. Отправитель запроса определяется по токену

**Контекст:** сервер должен сам определить, кто отправил запрос: от этого зависят проверка прав, запрет самоапрува и история. Имя, роль или автора в запросе указывает клиент, и подменить их ничего не стоит ([T-01](threat-model.md#t-01-действие-без-входа-или-от-имени-другого-пользователя)). Запрос без учётных данных или с неизвестными не должен выполнять ни одной операции O1–O10.

**Решение:**

*Какой токен.* Для каждого пользователя и каждого сервисного клиента команда при подготовке начальных данных создаёт токен: 32 случайных байта из криптографического генератора .NET (`RandomNumberGenerator`), записанные в base64url, - строку из 43 символов. Внутри токена нет ни имени, ни роли, это просто случайное значение. Готовые токены записываются в локальный файл вне Git, откуда участники берут их для запросов.

*Что хранит сервер.* В базе есть таблица учётных данных: хеш токена, ID пользователя или сервисного клиента, вид (человек или сервисный клиент) и признак, действует ли токен. Сам токен в базе не хранится.

*Как сервер проверяет запрос.* Клиент передаёт токен в заголовке `Authorization: Bearer <токен>`. Сервер считает SHA-256 от полученной строки и ищет запись с таким хешом. Если действующая запись нашлась, запрос выполняется от имени пользователя или сервисного клиента из этой записи. Если токена нет, запись не нашлась или токен отозван, запрос отклоняется до любой предметной операции. Без токена работает только `GET /health`.

*Автор и исполнитель.* Автор предложения и исполнитель в истории - всегда пользователь из записи токена. Поля вроде `author` в теле и заголовки с именем пользователя сервер не читает. Какие операции разрешены этому пользователю, определяет D-04.

*Что попадает в журналы.* Заголовок `Authorization` не входит в список заголовков, которые журнал запросов ASP.NET записывает целиком, поэтому вместо его значения в журнале стоит `[Redacted]`. Для разбора запросов в журнал пишется ID пользователя или сервисного клиента. В ответах сервера токен не возвращается.

**Обоснование:** выбор держится на трёх свойствах токена.

- Его невозможно угадать: 256 бит случайности делают перебор бессмысленным.
- Утечка базы не даёт рабочих токенов: в ней только хеши, а по хешу токен не восстановить. Соль и медленный хеш, как для паролей, не нужны: они защищают слабые пароли от перебора, а здесь перебирать нечего. Без соли сервер находит запись прямо по хешу, одним запросом к индексу.
- В токене нет прав, поэтому изменение назначений действует сразу, без перевыпуска токена.

Для одного сервера с одной базой этого достаточно. Подписанный токен с ролями внутри, например JWT, нужен, когда токен проверяют несколько сервисов без общей базы. У нас такого нет, а роли в токене устаревали бы после изменения списка апруверов ([T-09](threat-model.md#t-09-решение-апрувера-после-исключения-из-списка)).

**Связанные угрозы:** [T-01](threat-model.md#t-01-действие-без-входа-или-от-имени-другого-пользователя).

**Связанные требования:** [SR-01](security-requirements.md#sr-01-действие-выполняется-от-имени-аутентифицированного-пользователя), [SR-10](security-requirements.md#sr-10-действия-прослеживаются-история-не-стирается).

**Будущая проверка:**

#### D-01-P1. Токен хранится и принимается только как хеш

- **Ситуация:** A - редактор C, у него есть токен.
- **Действие:** найти исходную строку токена A в файле базы и в журнале сервера. Запросить версии (C, dev) (O1) с токеном A, затем с хешом токена A из базы вместо токена, затем без заголовка `Authorization`.
- **Ожидаемый результат:** исходного токена нет ни в базе, ни в журнале; в журнале вместо заголовка стоит `[Redacted]`. Запрос с токеном выполняется, с хешом и без токена - отклоняется, предметное состояние не меняется. Критерии: SR-01, пп. 1–2.

#### D-01-P2. Автор берётся из токена, а не из запроса

- **Ситуация:** A - редактор C и апрувер prod C, B - другой пользователь.
- **Действие:** A отправляет предложение в (C, prod), указав в теле `author: B` и в заголовке имя B, затем одобряет это предложение.
- **Ожидаемый результат:** предложение создано с автором A, в истории исполнитель - A. Апрув отклоняется как самоапрув в prod. Критерии: SR-01, пп. 3–4; SR-04, п. 1; SR-10, п. 1.

**Ограничения и последствия:**

- Токен подтверждает только то, что запрос пришёл с этим токеном. Если токен украдут, вор действует от имени владельца, пока команда не отзовёт запись в базе.
- Срока действия у токена нет. Выдача и отзыв возможны только через начальные данные, API для этого нет.
- Без HTTPS токен передаётся открытым текстом. Это допустимо, пока сервер принимает запросы только с `127.0.0.1` (допущение модели угроз); для другого размещения нужен HTTPS.

### D-02. Команды меняют состояние и историю атомарно

**Контекст:** апрув состоит из нескольких шагов: прочитать текущую публикацию, проверить конфликты и схему, записать новую версию, сделать её текущей публикацией, обновить отметки полей и записать историю. Если шаги разных запросов перемешиваются или выполняются не все, публикация портится:

- два апрува одной пары идут одновременно, оба читают версию 5 и записывают каждый свою версию 6; второе изменение затирает первое ([T-06](threat-model.md#t-06-потеря-изменений-при-одновременных-апрувах));
- сервер записал новую версию и упал до записи истории: версия опубликована, а кто её выпустил, неизвестно;
- администратор удаляет апрувера, пока тот одобряет предложение: права проверены до удаления, а запись сделана после ([T-09](threat-model.md#t-09-решение-апрувера-после-исключения-из-списка)).

**Решение:**

*Одна команда - одна транзакция.* Отправка предложения (O4), апрув (O5), отклонение (O6), отзыв (O11) и изменение списка апруверов (O8) выполняются каждая в одной транзакции SQLite. Транзакция открывается командой `BEGIN IMMEDIATE`: она получает право записи сразу, ещё до чтения прав и состояния. Право записи занято на время одной серверной команды, включая её проверки и сохранение; другие пишущие транзакции в это время ждут. Это краткая очередь записи SQLite, а не резервирование конфигурации с момента отправки драфта до его апрува. Пользователи могут независимо подготовить несколько предложений для одной пары.

*Окончательные проверки - внутри транзакции.* В транзакции сервер заново читает назначения пользователя (D-04) и сохранённое предложение: оно должно быть в статусе `in_review`, при апруве в prod его автор не должен совпадать с пользователем, а при отзыве - должен совпадать. Поэтому из двух одновременных решений по одному предложению - апрува, отклонения или отзыва - выполняется только то, что первым получило право записи; второе видит, что предложение уже завершено, и отклоняется ([T-12](threat-model.md#t-12-отзыв-и-апрув-одного-предложения-одновременно)). Проверки до транзакции могут сразу отказать, но окончательное решение принимается только внутри неё. Поэтому удаление апрувера не может вклиниться между проверкой и записью.

*Как ищется конфликт.* Для каждого поля пары сервер хранит отметку изменения - номер версии, в которой поле последний раз меняло значение. Предложение с базовой версией N применяется, только если у каждого изменяемого поля отметка не больше N. Например, предложение основано на версии 5 и меняет `logLevel`. Если `logLevel` менялся в версии 6, будет конфликт, даже если в версии 7 его вернули к прежнему значению.

*Как применяется предложение.* Сам факт смены текущей версии после отправки предложения не является конфликтом. Проверяется только, менялись ли поля этого предложения; равенство `baseVersion` номеру текущей публикации не требуется. Сервер берёт текущую публикацию, а не базовую версию, и заменяет в ней только поля из сохранённого предложения. Остальные поля остаются как в текущей публикации. Затем по схеме проверяется вся получившаяся конфигурация, включая связи между полями и размер (D-03).

*Что записывается.* В той же транзакции сервер создаёт версию с номером на единицу больше текущего, делает её текущей публикацией пары, обновляет отметки изменённых полей, переводит предложение в `applied` и добавляет одну запись истории с исполнителем из D-01. Номер версии уникален в пределах пары - это ограничение уникальности в базе, поэтому двух версий 6 быть не может. Отклонение так же вместе записывает `rejected`, причину и историю, отзыв - `rejected` и запись об отзыве автором, изменение списка апруверов - список и историю. Если проверка не прошла или запись упала, транзакция откатывается целиком, и ничего из этого не появляется. Исключение - конфликт: транзакция не откатывается, а в ней предложение переводится в `rejected` с причиной «конфликт: поле изменено в версии N» и добавляется запись истории об автоматическом отклонении; версия, публикация и отметки полей не меняются. Если итоговая конфигурация не проходит схему, транзакция откатывается и предложение остаётся в `in_review`. Если право записи не освободилось за заданное время, сервер отвечает, что база занята; повторить можно только всю команду.

**Обоснование и сравнение вариантов:** чтобы проверка и запись не разошлись, в SQLite есть два способа.

| Способ | Как работает | Плюс | Минус |
| --- | --- | --- | --- |
| Сразу занять право записи (`BEGIN IMMEDIATE`) - **выбран** | Транзакция получает право записи до чтения прав и состояния | Пока команда проверяет, никто не может изменить проверяемые данные; порядок «проверить - записать» простой | Право записи занято и во время проверок, даже если команда в итоге откажет; остальные изменения ждут |
| Занять право записи только при записи (`BEGIN DEFERRED` в WAL) | Транзакция сначала читает и проверяет, а право записи берёт в момент записи. Если за это время кто-то записал данные, SQLite отказывает, и команду повторяют с начала | В WAL чтение и проверки могут идти параллельно с записью другой команды | Нужен повтор всей команды с ограниченным числом попыток. При повторе права нужно читать заново: старое разрешение мог отменить O8 |

Оба способа сохраняют отметки полей, проверку всей конфигурации и совместную запись, поэтому SR-06 выполняется в обоих. Если два драфта меняют разные поля, второй применяется к результату первого после повторного чтения текущего состояния; очередь транзакций не превращает его в конфликт. В обоих вариантах SQLite допускает только одного писателя: различается момент получения права записи и необходимость повтора, а не возможность одновременно выполнить две пишущие транзакции. Выбираем первый: команды короткие (одна пара, конфигурация до 16 КБ), и простой порядок для нас важнее времени ожидания. Пересмотреть выбор стоит, если замеры покажут, что команды заметно ждут друг друга. Тогда второй способ проверяется по D-02-P5.

**Пограничный случай.** Сначала мы считали, что два предложения, которые меняют разные поля, можно применить оба: конфликта по отметкам нет. Это неверно, если в схеме есть связь между полями. В примере из [T-10](threat-model.md#t-10-два-корректных-предложения-вместе-нарушают-схему) схема требует, чтобы `minPoolSize` был не больше `maxPoolSize`; в публикации 5 и 10. Одно предложение меняет `minPoolSize` на 8, другое - `maxPoolSize` на 6. Каждое по отдельности допустимо, а вместе они дают 8 и 6. После этого разбора мы:

- добавили угрозу T-10;
- уточнили SR-06: недопустимый итог отклоняется (п. 3), а два предложения применяются, только если допустим и каждый результат по отдельности, и общий (п. 5);
- в D-02 проверяем по схеме всю конфигурацию после применения, а не только изменённые поля;
- добавили проверку D-02-P2.

**Будущая проверка:** каждую проверку нужно выполнить на отдельной учебной базе. Одновременные запросы нужно отправлять через разные соединения, а не внутри одной общей тестовой транзакции.

#### D-02-P1. Одновременные апрувы и возврат значения

- **Ситуация:** текущая версия пары (C, prod) - 5. Подготовлены три случая: (а) два предложения от версии 5 меняют разные поля, `logLevel` и `requestTimeoutSeconds`; (б) два предложения от версии 5 меняют `logLevel`; (в) после версии 5 `logLevel` изменили, а затем вернули к прежнему значению, и на рассмотрении есть предложение от версии 5, которое тоже меняет `logLevel`.
- **Действие:** в случае (а) сначала одобрить более поздний драфт, затем более ранний, и повторить в обратном порядке. Отдельно в случаях (а) и (б) одобрить оба предложения одновременно: тестовый барьер отпускает оба запроса в один момент. В случае (в) одобрить старое предложение.
- **Ожидаемый результат:** (а) в каждом порядке применяются оба, появляются версии 6 и 7, последняя содержит оба изменения. Второй драфт не получает конфликт только из-за того, что текущая публикация уже не совпадает с его `baseVersion`. (б) применяется ровно одно, второе получает конфликт. (в) конфликт, хотя `old` совпадает с текущим значением. При конфликте версия не создаётся, отметки не меняются, предложение переходит в `rejected` с причиной о конфликте, в истории одна запись об автоматическом отклонении. Критерии: SR-06, пп. 1, 2, 4, 6.

#### D-02-P2. Связанные поля и размер итоговой конфигурации

- **Ситуация:** схема C требует, чтобы `minPoolSize` был не больше `maxPoolSize`; в текущей публикации 5 и 10. На рассмотрении два предложения из пограничного случая: `minPoolSize` → 8 и `maxPoolSize` → 6. В отдельной базе есть допустимое предложение, после которого полная конфигурация станет больше 16 384 байт.
- **Действие:** одобрить первое предложение, затем второе. В отдельной базе одобрить предложение с превышением размера.
- **Ожидаемый результат:** первое предложение применяется. Второе отклоняется с указанием нарушенной связи и остаётся в `in_review`, публикация сохраняет результат первого. Превышение размера тоже отклоняется без новой версии. Критерии: SR-06, п. 3; ограничение размера - [раздел 7 паспорта](../PROJECT.md#формат-и-проверка-конфигурации).

#### D-02-P3. Сбой посреди записи

- **Ситуация:** в тестовой сборке можно вызвать ошибку в заданной точке команды.
- **Действие:** для отправки предложения, апрува, отклонения, отзыва и изменения списка апруверов по очереди вызвать ошибку после записи данных, но до записи истории. Затем открыть базу заново.
- **Ожидаемый результат:** предметное состояние такое же, как до запроса: нет частичной версии, решения, изменения списка или записи истории. Предложение после неудачного апрува остаётся в `in_review`. Критерии: SR-06, п. 7; SR-10, п. 2.

#### D-02-P4. Удаление апрувера одновременно с его апрувом

- **Ситуация:** A - апрувер prod C, на рассмотрении предложение (C, prod) другого редактора.
- **Действие:** через два соединения выполнить удаление A из списка (O8) и апрув этого предложения от A (O5). Сначала первым получает право записи удаление, затем - апрув.
- **Ожидаемый результат:** если первым выполнилось удаление, апрув перечитывает список и отклоняется. Если первым выполнился апрув, он завершается до удаления, и его решение остаётся в истории; после удаления A ничего решать не может. Публикации по уже удалённому назначению не бывает. Критерии: SR-03, п. 3; SR-09, п. 8.

#### D-02-P5. Повтор команды во втором варианте

Это план проверки применимой альтернативы для сравнения с выбранным способом; реализовывать второй способ к EK1 не требуется.

- **Ситуация:** база работает в WAL; соединение X начало апрув по второму способу и уже прочитало права A и текущее состояние. После этого соединение Y удалило A из апруверов (O8).
- **Действие:** через X записать результат апрува.
- **Ожидаемый результат:** SQLite не даёт записать результат, прочитанный до изменения. X откатывается, повторяет команду с начала, заново читает права и отклоняется. Новой версии и записи истории об апруве нет.

#### D-02-P6. Отзыв одновременно с апрувом

- **Ситуация:** у редактора A есть предложение в (C, prod) в статусе `in_review`; B - апрувер prod C.
- **Действие:** через два соединения A отзывает предложение (O11), а B одобряет его (O5); тестовый барьер отпускает оба запроса в один момент. Повторить, меняя, кто первым получает право записи.
- **Ожидаемый результат:** выполняется ровно одна операция. Если первым апрув - предложение в `applied`, есть новая версия, отзыв отклонён как «предложение уже завершено». Если первым отзыв - предложение в `rejected`, новой версии нет, апрув отклонён так же. Статус, публикация и история согласованы, в истории одна запись. Критерии: SR-11, п. 4; SR-05, п. 4.

**Ограничения и последствия:**

- Защита работает, пока все записи идут через API. Изменение файла базы напрямую история не покажет (допущение модели угроз).
- Одновременно пишет только одна команда. Под большой нагрузкой запрос может не дождаться очереди и получить ответ, что база занята.
- Если ответ на апрув потерялся после записи, публикация уже произошла. Клиент проверяет статус предложения, а повторный апрув второй раз его не применит (SR-05, п. 4).
- Большая очередь записи, размещение базы на разных машинах или изменение схем через API потребуют пересмотреть решение. Несколько процессов с одной локальной базой SQLite сами по себе не нарушают её транзакции.
- Различие предметного конфликта и очереди записи сверено с [изоляцией SQLite](https://www.sqlite.org/isolation.html) и [правилами транзакций](https://www.sqlite.org/lang_transaction.html).

### D-03. YAML проверяется до построения данных и по схеме конфигурации

**Контекст:** редактор отправляет предложение изменений - YAML с `baseVersion` и `changes`. Он может прислать его с ошибками: повторяющийся ключ, строку `"60"` вместо числа, `null` там, где схема его запрещает, поле, которого нет в конфигурации. Такое предложение нельзя сохранять: после апрува ошибка дойдёт до потребителя. А может прислать YAML, специально составленный, чтобы остановить сервер: бомбу из алиасов или вложенность в тысячи уровней ([T-07](threat-model.md#t-07-затратный-yaml-останавливает-сервис)). Обычная загрузка YAML в объекты сначала строит весь документ в памяти и только потом даёт его проверить, а к этому моменту сервер уже мог упасть. Кроме того, текст ошибки библиотеки в ответе раскрывает устройство сервера.

**Решение:** предложение проверяется по шагам, и каждый следующий шаг выполняется, только если прошёл предыдущий.

*Шаг 1. Размер и кодировка.* Сервер читает тело запроса, пока не наберёт 16 384 байта. Если тело больше, чтение прекращается и запрос отклоняется. Заголовок `Content-Length` нужен только для того, чтобы отказать сразу; настоящий размер считается по прочитанным байтам. Принимается только `Content-Type: application/yaml`. Текст декодируется как UTF-8, недопустимая последовательность байтов означает отказ.

*Шаг 2. Структура YAML по событиям парсера.* YamlDotNet используется как потоковый парсер: он выдаёт по одному события вроде «начало документа», «ключ», «значение», «начало вложенного объекта» и сам ничего не строит. Сервер просматривает события и сразу отказывает, если встречает:

- второй документ;
- якорь, алиас, ключ слияния `<<` или пользовательский тег;
- нестроковый ключ или ключ, повторённый на одном уровне;
- вложенность глубже 8 уровней.

Бомба из алиасов отклоняется на первом же алиасе, до того как что-либо раскрыто. Глубина считается счётчиком, без рекурсии, поэтому вложенность в тысячи уровней не переполняет стек.

*Шаг 3. Содержимое и схема.* Структура предложения, базовая версия, `old` и ограничения значений проверяются по правилам [раздела 7 паспорта](../PROJECT.md#формат-и-проверка-конфигурации). Главное здесь - кто определяет тип значения. Его определяет сервер по правилам YAML 1.2 Core Schema, а не настройки YamlDotNet по умолчанию: `60` - целое число, `"60"` и `yes` - строки. Затем тип сверяется со схемой C из начальных данных, и тег в документе не может сменить ожидаемый тип поля.

*Шаг 4. Итоговая конфигурация при апруве.* Тот же валидатор проверяет всю конфигурацию после применения предложения (D-02) и размер полного YAML. Потребителю сервер выдаёт YAML, заново собранный из проверенных значений с явными типами, а не исходный текст предложения или версии: строки, похожие на число или логическое значение, остаются в кавычках, а `010` записывается как `10`. Так потребитель с другими правилами YAML прочитает то же значение, что проверил сервер ([T-11](threat-model.md#t-11-сервер-апрувер-и-потребитель-по-разному-понимают-значение)).

*Ответ об ошибке.* Сервер отвечает кодом нарушенного правила и при необходимости именем поля, например `duplicate_key: logLevel`. В ответ не попадают текст исключения библиотеки, стек вызовов, пути к файлам и сам документ. Ошибка в одном предложении не останавливает сервер.

**Обоснование:** каждый шаг дешевле следующего и отсекает то, что может навредить следующему. Лимит размера срабатывает раньше, чем сервер выделит память под документ. Проверка по событиям отклоняет опасные конструкции до того, как из текста построены данные, поэтому расход памяти и глубина стека не зависят от того, что прислал клиент. Тип значения определяет схема, которую задаёт команда, а не теги и настройки библиотеки, поэтому клиент не может сменить ожидаемый тип поля. Повторная проверка всей конфигурации при апруве ловит допустимые по отдельности изменения, которые вместе нарушают схему ([T-10](threat-model.md#t-10-два-корректных-предложения-вместе-нарушают-схему)).

**Связанные угрозы:** [T-07](threat-model.md#t-07-затратный-yaml-останавливает-сервис), [T-10](threat-model.md#t-10-два-корректных-предложения-вместе-нарушают-схему), [T-11](threat-model.md#t-11-сервер-апрувер-и-потребитель-по-разному-понимают-значение).

**Связанные требования:** [SR-07](security-requirements.md#sr-07-недопустимое-предложение-отклоняется-и-не-нарушает-работу-сервиса); [SR-06](security-requirements.md#sr-06-публикуется-только-бесконфликтный-и-допустимый-результат-целиком-или-никак) - проверка итоговой конфигурации перед публикацией; [SR-08](security-requirements.md#sr-08-сервисный-клиент-получает-только-текущую-конфигурацию-своей-пары) - выдача потребителю заново собранного YAML.

**Будущая проверка:** какие предложения должны отклоняться, перечисляет SR-07, пп. 1–12; каждый пункт проверяется своим примером. Проверки ниже касаются самого механизма.

#### D-03-P1. Опасный YAML отклоняется быстро, сервер продолжает работать

- **Ситуация:** у редактора C подготовлены три документа: бомба из алиасов меньше 1 КБ (10 уровней по 10 ссылок), документ с вложенностью в 5 000 уровней (около 10 КБ) и тело больше 16 384 байт без заголовка `Content-Length`.
- **Действие:** отправить каждый документ как предложение (O4), замеряя время ответа и память процесса. Сразу после этого другой пользователь вызывает `GET /health` и просмотр версий (O1).
- **Ожидаемый результат:** каждый документ отклоняется быстрее чем за секунду, без заметного роста памяти. Ответ называет нарушенное правило без внутренних подробностей. Сервер без перезапуска отвечает на оба следующих запроса. Критерии: SR-07, пп. 1, 4, 5, 11.

#### D-03-P2. Тип значения определяет сервер, а не библиотека

- **Ситуация:** схема C требует целое `requestTimeoutSeconds` от 1 до 120 и логическое `featureEnabled`.
- **Действие:** отправить предложения, где `new` для `requestTimeoutSeconds` равно `60`, `!!int 60`, `"60"`, `!!str 60`, `.nan`, `null` и `010`, а для `featureEnabled` - `yes`; последние два значения YAML 1.1 и 1.2 толкуют по-разному. Отдельно отправить корректный документ размером ровно 16 384 байта. После публикации допустимого предложения получить конфигурацию как потребитель.
- **Ожидаемый результат:** `60`, `!!int 60` и `010` принимаются, `010` - как 10 по YAML 1.2; `"60"`, `!!str 60`, `.nan`, `null` и `featureEnabled: yes` отклоняются. Документ ровно на границе размера принимается. У потребителя `requestTimeoutSeconds` - число, а `010` опубликовано как `10`, поэтому разбор по правилам YAML 1.1 тоже даёт 10. Строковые значения, похожие на числа, остаются строками. Критерии: SR-07, пп. 1, 9, 12; SR-08, п. 4; угроза T-11.

**Ограничения и последствия:**

- Лимиты удешевляют разбор одного документа, но не защищают от потока запросов (допущение модели угроз).
- Ошибка в самом YamlDotNet нашими проверками не закрывается; поведение парсера на опасных примерах подтверждает D-03-P1.
- Определение типов и проверку по схеме пишем сами. Ошибки в этом коде ловят D-03-P2 и примеры SR-07.

### D-04. Права и данные объекта берутся из базы

**Контекст:** D-01 определяет, кто отправил запрос, но не что ему разрешено. Проверка прав может ошибиться тремя способами:

- сервер верит данным из запроса: паре в адресе, окружению или изменениям в теле апрува ([T-02](threat-model.md#t-02-доступ-к-чужому-объекту-по-id), [T-05](threat-model.md#t-05-подмена-предложения-в-запросе-апрува));
- сервер проверяет правило операции не целиком: что пользователь апрувер, но не что он не автор ([T-03](threat-model.md#t-03-самоапрув-в-prod)); что пользователь вошёл, но не что он администратор ([T-04](threat-model.md#t-04-изменение-списка-апруверов-без-прав-администратора)); что запрос от сервисного клиента, но не от клиента какой пары ([T-08](threat-model.md#t-08-сервисный-клиент-выходит-за-пределы-своей-пары));
- сервер проверяет права по устаревшим сведениям, например по ролям, запомненным при входе ([T-09](threat-model.md#t-09-решение-апрувера-после-исключения-из-списка)).

**Решение:**

*Откуда берутся права.* Отдельной таблицы «токен → разрешённые операции» нет. Токен даёт только ID и вид отправителя (D-01), а права хранятся в таблицах назначений `editors`, `prod_approvers`, `admins` и `client_pairs`. Все они заполняются начальными данными; список апруверов prod меняет ещё и администратор через O8.

*Как проверяется операция.* Перед каждой операцией сервер заново читает из базы нужное назначение; между запросами ничего не запоминается. Правило для каждой операции:

| Операция | Что проверяет сервер |
| --- | --- |
| Просмотр версий, предложений, истории (O1–O3) пары (C, dev) | пользователь есть в `editors` для C |
| Просмотр (O1–O3) пары (C, prod) | пользователь есть в `editors` или `prod_approvers` для C |
| Отправка предложения (O4) | пользователь есть в `editors` для C |
| Апрув и отклонение (O5, O6) в dev | пользователь есть в `editors` для C |
| Апрув (O5) в prod | пользователь есть в `prod_approvers` для C и не является автором предложения |
| Отклонение (O6) в prod | пользователь есть в `prod_approvers` для C |
| Отзыв (O11) в dev и prod | пользователь - автор предложения и есть в `editors` для C |
| Просмотр списка апруверов prod конфигурации C (O7) | пользователь есть в `admins`, либо в `editors` или `prod_approvers` для C |
| Просмотр полного списка пользователей (O7), истории изменений списков (O9), изменение списка апруверов (O8) | пользователь есть в `admins` |
| Получение текущей конфигурации (O10) | отправитель - сервисный клиент, и пара есть в `client_pairs` для него |

O1–O9 и O11 разрешены только людям, O10 - только сервисным клиентам; это определяется по виду отправителя из D-01. Администратор может добавить себя в `prod_approvers` и одобрять чужие предложения prod, но своё одобрить не может по тому же правилу автора. Доступа к настройкам роль администратора сама по себе не даёт.

*Как находится объект.* Объект запроса сервер ищет сразу по ID и по паре из адреса. Например, для `GET /configs/C/envs/dev/proposals/42` (адрес условный) он ищет предложение с ID 42 именно в паре (C, dev), одним запросом к базе с обоими условиями. Если предложение 42 относится к другой конфигурации, сервер его не находит и отвечает «не найдено». Права проверяются для пары найденного объекта.

*Что берётся из сохранённого предложения.* Запросы апрува и отзыва содержат только ID предложения, а запрос отклонения - ещё и причину. Модель запроса в коде состоит только из этих полей, поэтому лишние поля из тела просто некуда прочитать. Пара, автор, базовая версия и изменения берутся из сохранённого предложения. Операций изменения отправленного предложения, опубликованной версии и истории в API нет. Сервисный клиент получает только текущую публикацию: номера версии в O10 нет.

**Обоснование:** права и данные объекта сервер берёт из одного места, из базы, поэтому клиент не может повлиять на проверку ничем, кроме своего токена. Права читаются при каждом запросе, поэтому исключение из списка апруверов действует сразу, а не после повторного входа. Поиск объекта сразу по ID и паре объединяет проверку прав и выборку данных: нельзя проверить права для одной пары, а загрузить объект из другой. Все правила собраны в одной таблице, совпадающей с [таблицей операций SR](security-requirements.md#термины-в-критериях-приёмки), и по ней же пишутся тесты.

**Будущая проверка:** что должно получиться для каждой роли и операции, задают критерии SR-02, SR-03, SR-04, SR-08 и SR-09. Проверки ниже проверяют сам механизм. Права на списки апруверов (O7–O9) и ограничение сервисного клиента своей парой проверяются прямо по критериям SR-09, пп. 1–4, и SR-08, пп. 1–3: это те же правила из таблицы.

#### D-04-P1. Объект ищется по ID и паре вместе

- **Ситуация:** A - редактор C. В другой конфигурации, где у A нет назначений, есть предложение 42 и версия 3.
- **Действие:** A запрашивает предложение 42 и версию 3 через адрес пары (C, dev), затем через тот же адрес одобряет и отклоняет предложение 42.
- **Ожидаемый результат:** все запросы получают ответ «не найдено». Данные чужой конфигурации не возвращаются, предметное состояние не меняется. Критерии: SR-02, п. 1; SR-03, п. 1.

#### D-04-P2. В prod апрувер не может быть автором

- **Ситуация:** A - редактор C и апрувер prod C. Администратор B - тоже редактор C и добавил себя в апруверы prod C. У каждого есть своё предложение в (C, prod).
- **Действие:** A и B по очереди одобряют свои предложения, затем - предложения друг друга.
- **Ожидаемый результат:** свои предложения не одобряются ни у A, ни у B; чужие одобряются. Критерии: SR-04, пп. 1, 3.

#### D-04-P3. Лишние поля в запросе апрува не используются

- **Ситуация:** у редактора A есть предложение в (C, dev) и предложение в (C, prod). B - апрувер prod C.
- **Действие:** A одобряет своё предложение (C, dev), добавив в тело `environment: prod`. B одобряет предложение A в (C, prod), добавив в тело свои изменения полей.
- **Ожидаемый результат:** первое предложение публикуется только в (C, dev), текущая публикация (C, prod) от него не меняется. Во втором публикуются только сохранённые изменения A. Критерии: SR-05, пп. 2, 5.

#### D-04-P4. Права читаются при каждом запросе

- **Ситуация:** A - апрувер prod C, на рассмотрении есть предложение (C, prod) другого редактора. Администратор удаляет A из списка апруверов (O8).
- **Действие:** A с тем же токеном одобряет и отклоняет это предложение.
- **Ожидаемый результат:** оба запроса отклоняются, хотя токен A не перевыпускался. Критерии: SR-03, п. 3; SR-09, п. 8. Удаление апрувера одновременно с его апрувом проверяет D-02-P4.

#### D-04-P5. Отозвать может только автор

- **Ситуация:** у редактора A есть предложения в (C, dev) и (C, prod) в статусе `in_review`, и одно уже применённое. B - другой редактор C, X - апрувер prod C без назначения редактора, Y - редактор другой конфигурации.
- **Действие:** B, X и Y по очереди отзывают предложения A, Y - через адрес своей конфигурации с ID предложения A. Затем A отзывает оба своих предложения `in_review` и применённое.
- **Ожидаемый результат:** запросы B, X и Y отклоняются, предложения A не меняются. Оба отзыва A выполняются, предложения переходят в `rejected`, в истории записи об отзыве автором. Отзыв применённого отклоняется. Критерии: SR-11, пп. 1–3.

**Ограничения и последствия:**

- Каждый запрос дополнительно читает назначения из базы. Для одного сервера и небольших таблиц это дёшево.
- Назначения редакторов и администраторов и доступ сервисных клиентов меняются только через начальные данные. Удаление из апруверов не снимает остальных назначений пользователя.
- Администратору доверяют: он может сменить состав апруверов prod целиком (допущение модели угроз).
