# Требования безопасности ConfigRelease

## Термины в критериях приёмки

В критериях C и D обозначают любые две разные конфигурации, E - любое окружение (dev или prod), A и B - любых двух разных пользователей.

**Объекты:**

- Пара (C, E) - конфигурация C в окружении E (dev или prod).
- Предложение - список изменений полей с базовой версией. Статусы: `in_review` → `applied` или `in_review` → `rejected`.
- Версия - полный набор настроек пары, созданный при апруве предложения. Номер версии растёт отдельно для каждой пары.
- Текущая публикация пары - версия, которую сервис сейчас выдаёт потребителям этой пары.
- Отметка изменения поля - номер версии пары, в которой поле последний раз меняло значение. Хранится сервером.

**Назначения:**

- Редактор конфигурации C - пользователь, назначенный редактором C начальными данными. Назначение действует для обоих окружений C.
- Апрувер prod конфигурации C - пользователь из текущего списка апруверов prod конфигурации C. Список меняет администратор.
- Администратор - пользователь, который управляет списками апруверов prod всех конфигураций. Назначается начальными данными при настройке сервиса; через API назначить администратора нельзя.
- Сервисный клиент пары (C, E) - клиент, которому начальными данными выдан доступ к этой паре.

Один пользователь может иметь несколько назначений одновременно.

**Операции API:**

| Код | Операция | Кому разрешена |
| --- | --- | --- |
| O1 | Просмотр версий пары (C, E), включая текущую публикацию | (C, dev): редактору C. (C, prod): редактору C и апруверу prod C |
| O2 | Просмотр предложений пары (C, E) | так же, как O1 |
| O3 | Просмотр истории пары (C, E) | так же, как O1 |
| O4 | Отправка предложения в пару (C, E) | редактору C |
| O5 | Апрув предложения пары (C, E) | (C, dev): редактору C, в том числе автору. (C, prod): апруверу prod C, если он не автор |
| O6 | Отклонение предложения пары (C, E) с причиной | (C, dev): редактору C. (C, prod): апруверу prod C |
| O7 | Просмотр списков пользователей и апруверов prod | список пользователей: администратору. Список апруверов prod конфигурации C: администратору, редактору C и апруверу prod C |
| O8 | Изменение списка апруверов prod конфигурации C | администратору |
| O9 | Просмотр истории изменений списков апруверов | администратору |
| O10 | Получение текущей конфигурации пары (C, E) | сервисному клиенту пары (C, E) |

`GET /health` к предметным операциям не относится и доступен всем.

**Результаты:**

- Действительные учётные данные - учётные данные, которые сервис связывает с конкретным пользователем или сервисным клиентом. Отсутствующие, пустые, искажённые и неизвестные сервису учётные данные недействительны.
- Аутентифицированный пользователь - пользователь или сервисный клиент, которого сервер определил по действительным учётным данным запроса.
- Запрос отклоняется - сервер возвращает ответ об ошибке, операция не выполняется, а ответ не содержит настроек, предложений, записей истории и списков назначений.
- Предметное состояние - то, что хранит сервис: предложения (содержимое, автор, пара, базовая версия, статус), версии, текущие публикации, отметки изменения полей, списки апруверов prod и записи истории. Если в критерии сказано, что предметное состояние не меняется, значит, после запроса все эти данные остались такими же, как до него.

## Требования

### SR-01. Действие выполняется от имени аутентифицированного пользователя

**Требование:** операции O1–O10 выполняются только для запросов с действительными учётными данными. Автором предложения и исполнителем решения или изменения списка считается аутентифицированный пользователь, данные о пользователе, переданные в самом запросе, на это не влияют.

**Обоснование:** на личности исполнителя держатся проверки прав (SR-02, SR-03, SR-09), запрет одобрять своё предложение в prod (SR-04) и история (SR-10). Если исполнителя можно подменить, все они теряют смысл.

**Критерий приёмки:**

1. **Ситуация:** запрос к любой из операций O1–O10 приходит без учётных данных, с пустыми или с недействительными учётными данными.\
   **Результат:** запрос отклоняется; предметное состояние не меняется.
2. **Ситуация:** запрос `GET /health` приходит без учётных данных.\
   **Результат:** сервер возвращает обычный ответ о работоспособности; ответ не содержит настроек, предложений и истории.
3. **Ситуация:** аутентифицированный пользователь A вызывает одну из операций O4, O5, O6, O8 с допустимыми предметными данными и указывает в параметре или заголовке запроса пользователя B как автора или исполнителя. У A нет прав на эту операцию, у B есть.\
   **Результат:** запрос отклоняется; предметное состояние не меняется.
4. **Ситуация:** то же, что в п. 3, но у A есть права на эту операцию.\
   **Результат:** операция выполняется; автором предложения или исполнителем действия в предложении и в истории записан A; B нигде не записан как автор или исполнитель.

**Приоритет:** высокий - без этого свойства не работают остальные ограничения доступа.

**Связанные T / D:** [T-01](threat-model.md#t-01-подмена-исполнителя-через-поле-запроса); [D-01](design-decisions.md#d-01-субъект-и-полномочия-определяются-сервером), [D-02](design-decisions.md#d-02-команды-меняют-состояние-и-историю-атомарно).

### SR-02. Данные конфигурации доступны только по назначениям

**Требование:** просматривать версии, предложения и историю пары (O1–O3) и отправлять в неё предложения (O4) можно только в соответствии с таблицей операций. Назначение администратора само по себе доступа к настройкам и предложениям не даёт.

**Обоснование:** настройки и планируемые изменения раскрывают внутренние параметры приложений. Отправка предложения в чужую конфигурацию позволяет готовить к выпуску изменения, за которые пользователь не отвечает.

**Критерий приёмки:**

1. **Ситуация:** пользователь, который не редактор C, запрашивает версии, предложения или историю пары (C, dev).\
   **Результат:** запрос отклоняется; данные не возвращаются.
2. **Ситуация:** пользователь, который не редактор C и не апрувер prod C, запрашивает версии, предложения или историю пары (C, prod).\
   **Результат:** запрос отклоняется; данные не возвращаются.
3. **Ситуация:** апрувер prod C, который не редактор C, запрашивает версии, предложения или историю пары (C, dev) либо любой пары другой конфигурации D, где у него нет назначений.\
   **Результат:** запрос отклоняется; данные не возвращаются.
4. **Ситуация:** администратор, у которого нет назначений редактора или апрувера C, запрашивает версии, предложения или историю любой пары C.\
   **Результат:** запрос отклоняется; данные не возвращаются.
5. **Ситуация:** пользователь, который не редактор C (например, апрувер prod C или администратор), отправляет допустимое предложение в любую пару C.\
   **Результат:** запрос отклоняется; предложение не создаётся.
6. **Ситуация:** редактор C запрашивает версии, предложения и историю обеих пар C и отправляет допустимое предложение в любую из них.\
   **Результат:** данные возвращаются; предложение создаётся в статусе `in_review` с этим редактором в качестве автора.
7. **Ситуация:** апрувер prod C запрашивает версии, предложения и историю пары (C, prod).\
   **Результат:** данные возвращаются.

**Приоритет:** высокий - раскрытие и подмена настроек чужих конфигураций.

**Внешний источник:** OWASP ASVS `v5.0.0-8.2.2` - доступ к конкретному объекту данных только при наличии явного разрешения.

**Связанные T / D:** [T-02](threat-model.md#t-02-доступ-к-чужому-объекту-по-id); [D-01](design-decisions.md#d-01-субъект-и-полномочия-определяются-сервером).

### SR-03. Решение по предложению принимает только уполномоченный для окружения

**Требование:** решение по предложению пары (C, dev) может принять любой редактор C, в том числе автор предложения. Решение по предложению пары (C, prod) принимает только пользователь, который входит в список апруверов prod C на момент решения. Это выполняется и при прямом обращении к операции API.

**Обоснование:** апрув сразу публикует изменения, с которыми работают приложения. Неуполномоченное решение выводит в prod непроверенные настройки. Решение пользователя, исключённого из списка, обходит контроль администратора над тем, кто выпускает в prod. Кроме того, в истории (SR-10) такое решение записывается от имени человека, у которого не было права его принимать, и история перестаёт отражать, кто на самом деле отвечал за выпуск.

**Критерий приёмки:**

1. **Ситуация:** пользователь, который не редактор C, вызывает апрув или отклонение предложения пары (C, dev) в статусе `in_review`.\
   **Результат:** запрос отклоняется; предметное состояние не меняется.
2. **Ситуация:** пользователь, который не входит в текущий список апруверов prod C, вызывает апрув или отклонение предложения пары (C, prod) в статусе `in_review`. Это может быть редактор C, апрувер prod другой конфигурации или администратор.\
   **Результат:** запрос отклоняется; предметное состояние не меняется.
3. **Ситуация:** пользователь входил в список апруверов prod C, когда предложение было отправлено, но администратор исключил его до решения. Он вызывает апрув или отклонение этого предложения.\
   **Результат:** запрос отклоняется; предметное состояние не меняется.
4. **Ситуация:** редактор C одобряет предложение пары (C, dev), в том числе своё.\
   **Результат:** предложение применяется по правилам SR-06.
5. **Ситуация:** апрувер prod C, который не автор предложения, одобряет предложение пары (C, prod) или отклоняет его с непустой причиной.\
   **Результат:** при апруве предложение применяется по правилам SR-06. При отклонении оно переходит в `rejected`, причина сохранена, текущая публикация не меняется.

**Приоритет:** высокий - прямое влияние на настройки prod.

**Связанные T / D:** [T-02](threat-model.md#t-02-доступ-к-чужому-объекту-по-id), [T-09](threat-model.md#t-09-решение-апрувера-после-исключения-из-списка); [D-01](design-decisions.md#d-01-субъект-и-полномочия-определяются-сервером), [D-02](design-decisions.md#d-02-команды-меняют-состояние-и-историю-атомарно).

### SR-04. Нельзя одобрить собственное предложение в prod

**Требование:** автор предложения пары (C, prod) не может его одобрить, даже если входит в список апруверов prod C или является администратором. Для dev этот запрет не действует.

**Обоснование:** рассмотрение в prod имеет смысл, только если изменения проверяет второй человек. Иначе пользователь, совмещающий назначения редактора и апрувера, выпускает свои изменения в prod без проверки.

**Критерий приёмки:**

1. **Ситуация:** пользователь - редактор C и апрувер prod C. Он отправил предложение в пару (C, prod) и вызывает его апрув.\
   **Результат:** запрос отклоняется; предложение остаётся в `in_review`; предметное состояние не меняется.
2. **Ситуация:** то же, что в п. 1, но вместо апрува автор отклоняет своё предложение с причиной.\
   **Результат:** предложение переходит в `rejected`: запрет касается только апрува.
3. **Ситуация:** другой апрувер prod C одобряет предложение из п. 1.\
   **Результат:** предложение применяется по правилам SR-06.

**Приоритет:** высокий - обходит рассмотрение в prod.

**Связанные T / D:** [T-03](threat-model.md#t-03-самоапрув-в-prod); [D-01](design-decisions.md#d-01-субъект-и-полномочия-определяются-сервером), [D-02](design-decisions.md#d-02-команды-меняют-состояние-и-историю-атомарно).

### SR-05. Отправленное предложение и опубликованная версия не меняются

**Требование:** после того как сервер принял и сохранил предложение (O4), его содержимое, автор, конфигурация, окружение и базовая версия не меняются. Опубликованная версия не меняется. Завершённое предложение (`applied` или `rejected`) нельзя применить или отклонить повторно.

**Обоснование:** апрувер одобряет конкретные изменения для конкретного окружения. Если их можно поменять после рассмотрения, применится то, что никто не проверял. Смена окружения переносит изменение, одобренное автором в dev, в prod без рассмотрения (обход SR-04). Смена автора обходит SR-04, изменение опубликованной версии - историю (SR-10).

**Критерий приёмки:**

1. **Ситуация:** любой пользователь отправляет запрос на изменение содержимого, автора, конфигурации, окружения или базовой версии существующего предложения в любом статусе.\
   **Результат:** запрос отклоняется; предложение прежнее.
2. **Ситуация:** в запросе апрува или отклонения (O5, O6) дополнительно передаются другие изменения, другая базовая версия или другое окружение.\
   **Результат:** переданные значения не используются; применяется или отклоняется предложение в том виде, в каком оно было отправлено. Сама операция выполняется или отклоняется по правилам SR-03, SR-04 и SR-06.
3. **Ситуация:** любой пользователь отправляет запрос на изменение или удаление опубликованной версии.\
   **Результат:** запрос отклоняется; версия прежняя.
4. **Ситуация:** уполномоченный пользователь вызывает апрув или отклонение предложения в статусе `applied` или `rejected`.\
   **Результат:** запрос отклоняется; предметное состояние не меняется.
5. **Ситуация:** автор одобряет своё предложение в пару (C, dev).\
   **Результат:** меняется только текущая публикация (C, dev); текущая публикация (C, prod) и предложения пары (C, prod) не меняются.

**Приоритет:** средний. Нарушение подрывает смысл рассмотрения. Но в ядре API нет операций редактирования предложений и версий, поэтому свойство держится в основном на их отсутствии, и сценарий маловероятен.

**Связанные T / D:** [T-05](threat-model.md#t-05-подмена-окружения-в-запросе-апрува); [D-01](design-decisions.md#d-01-субъект-и-полномочия-определяются-сервером), [D-02](design-decisions.md#d-02-команды-меняют-состояние-и-историю-атомарно).

### SR-06. Публикуется только бесконфликтный и допустимый результат, целиком или никак

**Требование:** апрув применяет предложение к текущей публикации пары, только если ни одно из изменяемых полей не менялось после базовой версии предложения и вся получившаяся конфигурация соответствует схеме C. Применение всех полей, создание версии, обновление текущей публикации, отметок полей и истории происходят вместе; при отказе или сбое не меняется ничего из этого.

**Обоснование:** без проверки конфликтов апрув старого предложения молча затирает более позднее изменение того же поля. Без проверки всего результата допустимые по отдельности изменения дают недопустимую конфигурацию. Частичное применение оставляет потребителей с конфигурацией, которую никто не одобрял.

**Критерий приёмки:**

1. **Ситуация:** уполномоченный пользователь одобряет предложение с базовой версией N, а ни одно из изменяемых полей после версии N не менялось, и итоговая конфигурация соответствует схеме.\
   **Результат:** создаётся версия с номером на единицу больше текущего; изменяемые поля получают новые значения; все остальные поля равны полям предыдущей текущей публикации; версия становится текущей публикацией пары; предложение переходит в `applied`; в истории одна запись о применении.
2. **Ситуация:** одобряется предложение, у которого хотя бы одно изменяемое поле менялось после базовой версии, даже если потом вернулось к прежнему значению.\
   **Результат:** сервер сообщает о конфликте и называет поле; текущая публикация, версии, отметки полей не меняются; предложение остаётся в `in_review`.
3. **Ситуация:** одобряется предложение, у которого каждое изменение по отдельности допустимо, но итоговая конфигурация нарушает схему (например, связь между полями).\
   **Результат:** запрос отклоняется с указанием нарушения; текущая публикация, версии и отметки полей не меняются.
4. **Ситуация:** два предложения пары с одной базовой версией меняют одно и то же поле, и их одобряют одновременно.\
   **Результат:** применяется ровно одно из них; второе получает конфликт по п. 2. В итоговой версии значение поля - из применённого предложения.
5. **Ситуация:** два предложения пары с одной базовой версией меняют разные поля, и их одобряют по очереди. Результат применения каждого предложения по отдельности и обоих вместе соответствует схеме.\
   **Результат:** оба применяются; итоговая конфигурация содержит изменения обоих.
6. **Ситуация:** то же, что в п. 5, но предложения одобряют одновременно.\
   **Результат:** оба применяются и создают две версии с разными последовательными номерами; двух версий с одним номером не появляется. Последняя версия содержит изменения обоих предложений: применение одного не возвращает поле, изменённое другим, к прежнему значению.
7. **Ситуация:** во время применения предложения происходит сбой (например, ошибка записи в базу).\
   **Результат:** текущая публикация, версии, отметки полей и история остаются такими же, как до апрува; предложение остаётся в `in_review`.

**Приоритет:** высокий. Потребители могут получить конфигурацию с потерянными изменениями или противоречивыми значениями. Особых условий для этого не нужно: достаточно в обычной работе одобрить старое предложение. Одновременные апрувы и сбой записи добавляют ещё два пути.

**Связанные T / D:** [T-06](threat-model.md#t-06-потеря-изменений-при-одновременных-апрувах), [T-10](threat-model.md#t-10-два-корректных-предложения-вместе-нарушают-схему); [D-02](design-decisions.md#d-02-команды-меняют-состояние-и-историю-атомарно), [D-03](design-decisions.md#d-03-yaml-разбирается-ограниченно-и-проверяется-по-доверенной-схеме).

### SR-07. Недопустимое предложение отклоняется и не нарушает работу сервиса

**Требование:** предложение, не соответствующее правилам раздела 7 паспорта «Формат и проверка конфигурации», отклоняется при отправке и не сохраняется. Обработка недопустимого предложения не приводит к аварийному завершению сервиса. После отклонения сервис продолжает обрабатывать разрешённые запросы.

**Обоснование:** предложение - недоверенный ввод от редактора. Недопустимые значения могут дойти до prod, а специально подобранный YAML может исчерпать память или время сервера.

**Критерий приёмки:**

Во всех пунктах 1-10 предложение в пару (C, E) отправляет редактор C, то есть права на отправку у него есть.

1. **Ситуация:** размер тела запроса больше 16 384 байт.
2. **Ситуация:** тело не в кодировке UTF-8, содержит больше одного YAML-документа или не является синтаксически корректным YAML.
3. **Ситуация:** в корне есть что-то кроме `baseVersion` и `changes`, `changes` пуст, или у поля в `changes` есть что-то кроме `old` и `new`.
4. **Ситуация:** есть нестроковый или повторяющийся ключ на любом уровне, либо вложенность глубже 8 уровней.
5. **Ситуация:** в теле есть якорь, алиас, ключ слияния или пользовательский тег.
6. **Ситуация:** `baseVersion` не положительное целое число или не номер существующей опубликованной версии этой же пары.
7. **Ситуация:** изменяемого поля нет в схеме C или в базовой версии.
8. **Ситуация:** `old` не совпадает со значением поля в базовой версии, или `old` равен `new`.
9. **Ситуация:** `new` не того типа, что требует схема, или нарушает её ограничения. В том числе: строка вместо числа (`"60"` вместо `60`), стандартный тег другого типа, бесконечность или NaN, `null` для поля, где схема его не допускает.
10. **Ситуация:** значения вложенные (объект или список), хотя изменять можно только поля верхнего уровня со скалярными значениями.

**Результат для пп. 1-10:** запрос отклоняется; предложение не создаётся. Ответ называет нарушенное правило и не содержит текста исключений, трассировки стека, путей к файлам и других внутренних подробностей сервера.

11. **Ситуация:** сразу после отклонения предложения из пп. 1-10 другой пользователь выполняет `GET /health` и разрешённый ему просмотр версий (O1).\
    **Результат:** сервер продолжает работать без перезапуска; оба запроса выполняются и возвращают обычный ответ.
12. **Ситуация:** редактор C отправляет предложение, которое удовлетворяет всем правилам.\
    **Результат:** предложение создаётся в статусе `in_review`; его изменения совпадают с отправленными.

**Приоритет:** высокий - основной канал внешнего ввода.

**Связанные T / D:** [T-07](threat-model.md#t-07-затратный-yaml-останавливает-сервис); [D-03](design-decisions.md#d-03-yaml-разбирается-ограниченно-и-проверяется-по-доверенной-схеме).

### SR-08. Сервисный клиент получает только текущую конфигурацию своей пары

**Требование:** сервисный клиент может только получать текущую публикацию той пары, к которой у него есть доступ (O10). Операция O10 доступна только сервисным клиентам. Ответ содержит только полную конфигурацию, без служебных данных предложений и истории.

**Обоснование:** учётные данные сервисного клиента хранятся в приложении-потребителе и могут утечь. Их возможности должны ограничиваться одной текущей конфигурацией, без доступа к предложениям, другим парам, истории и изменениям.

**Критерий приёмки:**

1. **Ситуация:** аутентифицированный сервисный клиент пары (C, E) запрашивает текущую конфигурацию другой пары: (C, другое окружение) или любой пары другой конфигурации.\
   **Результат:** запрос отклоняется; конфигурация другой пары не возвращается.
2. **Ситуация:** аутентифицированный сервисный клиент пары (C, E) вызывает любую из операций O1–O9, даже для своей пары.\
   **Результат:** запрос отклоняется; предметное состояние не меняется.
3. **Ситуация:** запрос текущей конфигурации (O10) приходит без действительных учётных данных сервисного клиента: без учётных данных, с недействительными или с действительными учётными данными пользователя-человека.\
   **Результат:** запрос отклоняется; конфигурация не возвращается.
4. **Ситуация:** аутентифицированный сервисный клиент пары (C, E) запрашивает её текущую конфигурацию.\
   **Результат:** сервер возвращает полную конфигурацию текущей публикации (C, E) в YAML; ответ не содержит `baseVersion`, `changes`, `old`/`new`, авторов и других служебных данных предложений.

**Приоритет:** высокий - граница с машинными клиентами.

**Связанные T / D:** [T-08](threat-model.md#t-08-утёкший-токен-потребителя-читает-чужое-окружение); [D-01](design-decisions.md#d-01-субъект-и-полномочия-определяются-сервером).

### SR-09. Списки апруверов prod меняет только администратор

**Требование:** список апруверов prod конфигурации C видят только её редакторы, её апруверы prod и администратор. Полный список пользователей и историю изменений списков апруверов (O9) видит только администратор. Изменять список апруверов prod конфигурации (O8) тоже может только администратор, и только добавлять или удалять существующих пользователей. Через API нельзя менять назначения редакторов, доступ сервисных клиентов и список администраторов. Изменение списка сразу определяет, кто может принимать решения в prod (SR-03), и не меняет предложения, решения и публикации.

**Обоснование:** список апруверов определяет, кто выпускает изменения в prod. Если его может изменить кто-то кроме администратора, пользователь добавит себя или сообщника и обойдёт рассмотрение. Списки назначений раскрывают права пользователей: по ним видно, чьи учётные данные дают доступ к prod. Поэтому список апруверов конфигурации видят только те, кому он нужен для работы: её редакторы, которым нужно знать, к кому обратиться за апрувом, и её апруверы, которые делят ответственность за выпуск.

**Критерий приёмки:**

1. **Ситуация:** пользователь, который не администратор (например, редактор C или апрувер prod C), вызывает добавление или удаление апрувера prod C, даже себя.\
   **Результат:** запрос отклоняется; список апруверов не меняется; записей истории о списке нет.
2. **Ситуация:** пользователь, который не администратор, запрашивает полный список пользователей или историю изменений списков апруверов (O9).\
   **Результат:** запрос отклоняется; список и записи истории не возвращаются.
3. **Ситуация:** пользователь, который не редактор C, не апрувер prod C и не администратор (например, редактор или апрувер prod другой конфигурации D), запрашивает список апруверов prod C.\
   **Результат:** запрос отклоняется; список не возвращается.
4. **Ситуация:** редактор C или апрувер prod C запрашивает список апруверов prod C.\
   **Результат:** сервер возвращает текущий список апруверов prod C; списки других конфигураций и история изменений в ответ не входят.
5. **Ситуация:** администратор добавляет в список апруверов prod C несуществующего пользователя.\
   **Результат:** запрос отклоняется; список не меняется.
6. **Ситуация:** любой пользователь, даже администратор, вызывает изменение назначений редакторов, доступа сервисных клиентов или списка администраторов.\
   **Результат:** запрос отклоняется; назначения не меняются.
7. **Ситуация:** администратор добавляет существующего пользователя в список апруверов prod C.\
   **Результат:** пользователь сразу может одобрять чужие предложения пары (C, prod) и отклонять предложения этой пары, включая собственные, по правилам O5 и O6; предложения, версии и текущие публикации не меняются; в истории запись об изменении списка апруверов.
8. **Ситуация:** администратор удаляет пользователя из списка апруверов prod C.\
   **Результат:** пользователь больше не может принимать решения по (C, prod) (SR-03, п. 3); его прежние решения и опубликованные версии не меняются; в истории запись об изменении.

**Приоритет:** высокий - изменение списка открывает путь в prod в обход рассмотрения.

**Связанные T / D:** [T-04](threat-model.md#t-04-изменение-списка-апруверов-без-прав-администратора), [T-09](threat-model.md#t-09-решение-апрувера-после-исключения-из-списка); [D-01](design-decisions.md#d-01-субъект-и-полномочия-определяются-сервером), [D-02](design-decisions.md#d-02-команды-меняют-состояние-и-историю-атомарно).

### SR-10. Действия прослеживаются, история не стирается

**Требование:** для каждой успешной отправки предложения, апрува, отклонения и изменения списка апруверов сохраняется запись истории: действие, исполнитель, время, объект и подробности - изменённые поля с прежними и новыми значениями, номер созданной версии, причина отклонения, добавленный или удалённый пользователь. Через API записи истории нельзя изменить или удалить.

**Обоснование:** после неудачного выпуска нужно установить, кто предложил и кто одобрил изменение, а после изменения прав - кто их выдал. Если историю можно изменить, по ней нельзя разобрать инцидент и доказать, кто что сделал.

**Критерий приёмки:**

1. **Ситуация:** успешно выполнена одна из операций O4, O5, O6, O8.\
   **Результат:** в истории появляется ровно одна новая запись с действием, исполнителем, временем, объектом и подробностями. Исполнитель - аутентифицированный пользователь. Время задаёт сервер; значение времени из запроса не используется.
2. **Ситуация:** запрос на одну из операций O4, O5, O6, O8 отклонён по любой причине.\
   **Результат:** записи о выполненном действии не появляется.
3. **Ситуация:** любой пользователь, даже администратор, отправляет запрос на изменение или удаление записи истории.\
   **Результат:** запрос отклоняется; запись остаётся прежней.

Кто может просматривать историю, определяют SR-02 (история пары, O3) и SR-09 (история изменений списков, O9).

**Приоритет:** средний - не мешает выпуску напрямую, но нужен для разбора инцидентов и контроля прав.

**Связанные T / D:** [T-01](threat-model.md#t-01-подмена-исполнителя-через-поле-запроса); [D-01](design-decisions.md#d-01-субъект-и-полномочия-определяются-сервером), [D-02](design-decisions.md#d-02-команды-меняют-состояние-и-историю-атомарно).
