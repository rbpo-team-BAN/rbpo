# Модель угроз ConfigRelease

Документ описывает, как можно нарушить свойства безопасности ConfigRelease. Он опирается на [паспорт проекта](../PROJECT.md) и [требования безопасности SR](security-requirements.md): каждая угроза связана с требованием, которое она нарушает. Решения для угроз приоритетного набора описаны в [проектных решениях D](design-decisions.md).

## Термины

Конфигурация, предложение изменений, базовая версия, версия, окружение, апрув и текущая публикация понимаются так же, как в [паспорте](../PROJECT.md#термины). Роли и их права описаны в [разделе 3 паспорта](../PROJECT.md#3-пользователи-и-доступные-действия). Ниже - обозначения и термины, которые встречаются в этом документе.

- **C, D** - конфигурации. C - конфигурация, о которой идёт речь в угрозе; D - другая конфигурация, к которой у пользователя нет доступа.
- **E** - окружение: dev или prod.
- **Пара (C, E)** - настройки конфигурации C в окружении E. У каждой пары свои версии, предложения, текущая публикация и история. Например, (C, dev) и (C, prod) - две разные пары одной конфигурации.
- **Отметка изменения поля** - номер версии пары, в которой поле последний раз меняло значение. Её хранит сервер; по ней при апруве находят конфликты.
- **Учётные данные** - то, что клиент передаёт в запросе, чтобы сервер определил, кто его отправил. Каждые учётные данные связаны с одним пользователем или сервисным клиентом. Способ входа выбирается в проектных решениях.
- **Аутентифицированный пользователь** - пользователь или сервисный клиент, которого сервер определил по действительным учётным данным запроса.
- **Операции O1–O11** - операции API из [таблицы в SR](security-requirements.md#термины-в-критериях-приёмки), где указано, кому каждая из них разрешена. В угрозах рядом с кодом указывается название операции, например «апрув предложения (O5)».
- **Граница доверия** - место, где запрос переходит от стороны, которой сервер не может доверять, к самому серверу. Обозначается TB-01, TB-02.
- **Недоверенный ввод** - данные из запроса, корректность и допустимость которых сервер не может предполагать заранее: ID, окружение, YAML-предложение, решение, любые дополнительные поля.
- **Точка входа** - операция API, через которую недоверенный ввод попадает в продукт.
- **Угроза (T-01, T-02, …)** - конкретный сценарий: кто, каким запросом или при каком условии затрагивает объект продукта и что при этом нарушается.
- **Приоритетный набор** - угрозы, для которых выбираются проектные решения D.

## 1. Модель продукта

Компоненты и потоки данных показаны на схеме в [разделе 6 паспорта](../PROJECT.md#6-компоненты-и-внешние-взаимодействия): клиенты обращаются только к серверному API, прямого доступа к базе у них нет. Какие данные приходят в продукт и кто ими управляет, перечислено в [разделе 7 паспорта](../PROJECT.md#7-откуда-продукт-получает-данные).

**Точки входа** - операции API O1–O11 из [таблицы в SR](security-requirements.md#термины-в-критериях-приёмки) и `GET /health`. Любой запрос к ним может прийти без учётных данных, с чужими учётными данными или с лишними полями.

**Где принимаются решения.** Все решения принимает API: кто отправил запрос, разрешена ли ему операция, проходит ли предложение проверку по схеме, нет ли конфликта при апруве. База только хранит состояние: пользователей и назначения, схемы, предложения, версии, текущие публикации, отметки изменения полей и историю.

**Что может измениться.** Состояние меняют только пять операций: отправка предложения (O4), апрув и отклонение (O5, O6), отзыв предложения автором (O11) и изменение списка апруверов prod (O8). Остальные операции только читают данные.

### Что уже существует и что планируется

Сейчас реализован только `GET /health` ([раздел 9 паспорта](../PROJECT.md#9-стек-и-путь-к-первой-работающей-версии)). Он отвечает без учётных данных, не работает с базой и не выполняет предметных операций, поэтому угроз для него в модели нет.

Всё остальное на схеме - база, вход, проверка прав и YAML, предметные операции - пока проектируется. Угрозы описывают продукт таким, каким его задают паспорт и требования SR.

### Существенные допущения

- Сервер принимает запросы только с этого же компьютера (`127.0.0.1`, [раздел 10 паспорта](../PROJECT.md#10-локальный-запуск)), поэтому перехват учётных данных в сети не рассматривается.
- Компьютер, файл базы и начальные данные контролирует только команда. Изменение базы в обход API не рассматривается.
- Администратор - доверенное лицо. Злоупотребление его правом менять списки апруверов не рассматривается; одобрить своё предложение в prod он всё равно не может (T-03).
- Автор может отозвать предложение и отправить его заново, надеясь, что его рассмотрит другой апрувер. Это процессная проблема, а не обход проверки: каждая отправка и каждый отзыв видны в истории, и одобрить предложение всё равно должен апрувер.
- Защита от массового потока запросов (сетевого DDoS) - вне границ продукта. Рассматривается только перегрузка, которую вызывает содержимое одного запроса (T-07).

## 2. Границы доверия

Обе границы проходят по стрелкам от клиентов к API на схеме паспорта.

| Граница | Что пересекает | Почему требуется проверка |
| --- | --- | --- |
| TB-01. Пользователь или клиент без входа → API | Учётные данные; ID конфигурации, окружения, предложения и версии; YAML-предложение; решение и причина отказа; ID пользователя для списка апруверов | Клиент может отправить запрос к API напрямую, в обход обычного порядка действий: не передать учётные данные, подставить чужой ID или другое окружение, добавить лишние поля, прислать специально составленный YAML. Действительные учётные данные показывают, кто отправил запрос, но не доказывают, что ему разрешено это действие |
| TB-02. Сервисный клиент → API | Учётные данные сервисного клиента; конфигурация и окружение, настройки которых он запрашивает | Учётные данные хранятся в приложении-потребителе, вне контроля команды, и могут утечь. В запросе можно назвать любую пару, а не только ту, к которой у клиента есть доступ |

YAML-предложение пересекает TB-01 вместе с остальным запросом. Его разбирает уже сервер, но содержимое остаётся недоверенным, пока не пройдёт все проверки из [раздела 7 паспорта](../PROJECT.md#формат-и-проверка-конфигурации).

Внутри компьютера команды границ доверия нет. Начальные данные загружает команда, а после этого в базу пишет только API. Поэтому сервер может доверять сохранённому состоянию - назначениям, автору, паре и статусу предложения, - но не тому, что о них сказано в запросе.

## 3. Значимые объекты и свойства

Какие данные важны и что будет при их раскрытии или порче, описано в [разделе 5 паспорта](../PROJECT.md#5-значимые-данные-и-другие-объекты). Здесь - свойства, которые должны сохраняться, и угрозы, которые их нарушают.

| Объект | Что должно выполняться | Угрозы |
| --- | --- | --- |
| Версии, предложения и история пары | Их видят только пользователи с назначением на эту конфигурацию. Сервисный клиент получает только текущую публикацию своей пары | T-02, T-08 |
| Отправленное предложение | После отправки предложение не меняется: апрувер одобряет именно те изменения и для того окружения, которые указал автор | T-05 |
| Текущая публикация | Потребитель получает только одобренные изменения: в prod их проверил другой пользователь, ни одно одобренное изменение не потеряно, итоговая конфигурация соответствует схеме | T-03, T-06, T-10, T-11 |
| Учётные данные и назначения | Сервер сам определяет, кто отправил запрос, и проверяет права по назначениям на момент операции. Список апруверов prod меняет только администратор | T-01, T-04, T-09 |
| История | Для каждого действия записан настоящий исполнитель | T-01 |
| Работа сервиса | Некорректное предложение отклоняется, а сервис продолжает отвечать остальным пользователям и потребителям | T-07 |

## 4. Угрозы

Для каждой угрозы указаны: **ситуация** - кто и каким запросом или при каком условии затрагивает объект; **последствие** - что при этом нарушается; граница и точка входа; связанные SR; приоритет с обоснованием.

Приоритет оценивается по двум признакам: насколько тяжелы последствия и насколько реалистичен сценарий.

- **Высокий** - последствия тяжёлые: пользователь читает чужие настройки, в prod попадают изменения, которые никто не проверил, одобренные изменения теряются или сервис перестаёт отвечать. Особых условий для сценария не нужно: достаточно своих учётных данных и обычного запроса к API, либо сценарий возникает сам при обычной работе нескольких пользователей.
- **Средний** - последствия тяжёлые, но для сценария нужно редкое условие, например утечка чужих учётных данных или особая связь полей в схеме. Либо условие обычное, но последствия ограничены.

### T-01. Действие без входа или от имени другого пользователя

**Ситуация:** возможны два варианта.

- Запрос к операции приходит без учётных данных или с недействительными, а сервер всё равно его выполняет.
- Пользователь A входит со своими учётными данными и указывает в запросе другого пользователя B. Например, при отправке предложения (O4) добавляет в тело поле `author: B`. Сервер берёт автора из этого поля, а не из учётных данных.

Если у A есть настоящие учётные данные B, это уже утечка, а не подмена; для сервисного клиента такой сценарий описан в T-08.

**Последствие:** в первом варианте любой, кто может отправить запрос, читает и меняет настройки без входа. Во втором A действует от имени B: например, отправляет предложение в prod с автором B и сам его одобряет, обходя запрет самоапрува. В истории автором записан B.

**Граница / точка входа:** TB-01 - отправка предложения (O4), апрув и отклонение (O5, O6), отзыв (O11), изменение списка апруверов (O8); без учётных данных - любая операция O1–O9 или O11. TB-02 - получение текущей конфигурации (O10) без учётных данных.

**Связанные SR:** [SR-01](security-requirements.md#sr-01-действие-выполняется-от-имени-аутентифицированного-пользователя), [SR-10](security-requirements.md#sr-10-действия-прослеживаются-история-не-стирается).

**Приоритет:** высокий. Последствия тяжёлые: перестают работать проверки прав, запрет самоапрува и история. Особых условий не нужно: достаточно своих учётных данных и одного лишнего поля в запросе, а в первом варианте - вообще ничего.

### T-02. Доступ к чужому объекту по ID

**Ситуация:** пользователь A - редактор конфигурации C, но не D. Он отправляет запрос просмотра предложения (O2) по адресу своей конфигурации, но подставляет ID предложения конфигурации D, например `GET /configs/C/proposals/42` (адрес условный). Сервер проверяет, что A - редактор C, и загружает предложение 42 только по ID, не сверяя, что оно относится к C. Так же A может получить чужую версию (O1) или вызвать апрув, отклонение и отзыв (O5, O6, O11) чужого предложения. Отзыв чужого предложения возможен и внутри своей конфигурации, если сервер не сверяет исполнителя с автором.

**Последствие:** A читает настройки и предложения конфигурации D, к которой у него нет доступа. Через апрув он публикует в D изменения, которые не одобрял никто из её апруверов. Через отзыв он срывает чужой выпуск, например срочное исправление в prod.

**Граница / точка входа:** TB-01 - ID версии или предложения в просмотре (O1, O2), апруве, отклонении и отзыве (O5, O6, O11).

**Связанные SR:** [SR-02](security-requirements.md#sr-02-данные-конфигурации-доступны-только-по-назначениям), [SR-03](security-requirements.md#sr-03-решение-по-предложению-принимает-только-уполномоченный-для-окружения), [SR-11](security-requirements.md#sr-11-отозвать-предложение-может-только-его-автор-пока-оно-на-рассмотрении).

**Приоритет:** высокий. Последствия тяжёлые: раскрытие чужих настроек и публикация без прав. Особых условий не нужно: достаточно своих учётных данных и чужого ID. Номера версий идут по порядку, поэтому их легко подобрать.

### T-03. Самоапрув в prod

**Ситуация:** пользователь A - редактор C и апрувер prod C; паспорт разрешает совмещать эти роли. A отправляет предложение в пару (C, prod) и сам вызывает его апрув (O5). Сервер проверяет только, что A входит в список апруверов prod C, и не сравнивает его с автором предложения. Так же может поступить администратор, добавивший себя в апруверы.

**Последствие:** изменения A попадают в prod без проверки вторым человеком, и рассмотрение prod теряет смысл.

**Граница / точка входа:** TB-01 - апрув предложения (O5), ID своего предложения.

**Связанные SR:** [SR-04](security-requirements.md#sr-04-нельзя-одобрить-собственное-предложение-в-prod).

**Приоритет:** высокий. Последствие - непроверенные изменения в prod. Особых условий не нужно: совмещение ролей - обычная ситуация, а запрос апрува своего предложения ничем не отличается от разрешённого.

### T-04. Изменение списка апруверов без прав администратора

**Ситуация:** пользователь A - редактор C, но не администратор. Он вызывает изменение списка апруверов prod C (O8) и добавляет в него себя и другого пользователя B. Сервер проверяет только, что A вошёл, и не проверяет роль администратора.

**Последствие:** A и B одобряют предложения друг друга в prod C. Запрет самоапрува формально соблюдён, но решения в prod принимают те, кому администратор этого не разрешал.

**Граница / точка входа:** TB-01 - изменение списка апруверов prod (O8).

**Связанные SR:** [SR-09](security-requirements.md#sr-09-списки-апруверов-prod-меняет-только-администратор).

**Приоритет:** высокий. Список апруверов - единственный путь к выпуску в prod, и его изменение без прав - прямое повышение привилегий. Особых условий не нужно: достаточно учётных данных любого пользователя.

### T-05. Подмена предложения в запросе апрува

**Ситуация:** операции изменения отправленного предложения в API нет, но в запрос апрува (O5) можно добавить лишние поля. Возможны два варианта.

- Автор A отправил предложение в пару (C, dev) и вызывает его апрув - по правилам dev это разрешено. В тело запроса он добавляет `environment: prod`. Сервер проверяет права по сохранённому окружению dev, а публикует в окружение из запроса.
- Апрувер prod B одобряет предложение редактора A в паре (C, prod) и добавляет в тело запроса свои изменения полей. Сервер применяет изменения из запроса вместо сохранённых.

**Последствие:** в prod попадают изменения, которые не проверял второй человек: в первом варианте - изменения A, во втором - изменения B. Во втором варианте в истории их автором записан A.

**Граница / точка входа:** TB-01 - лишние поля в теле запроса апрува (O5).

**Связанные SR:** [SR-05](security-requirements.md#sr-05-отправленное-предложение-и-опубликованная-версия-не-меняются).

**Приоритет:** высокий. Последствие - непроверенные изменения в prod. Особых условий не нужно: достаточно прав редактора в dev или прав апрувера prod и одного лишнего поля в запросе.

### T-06. Потеря изменений при одновременных апрувах

**Ситуация:** в паре (C, prod) на рассмотрении два предложения с базовой версией 5: одно меняет `logLevel`, другое - `requestTimeoutSeconds`. Два апрувера одобряют их одновременно. Оба запроса читают версию 5, каждый применяет к ней своё изменение и записывает результат как версию 6. Злоумышленник для этого не нужен, но и один пользователь может намеренно отправить два апрува одновременно - например, в dev, где он одобряет предложения сам.

**Последствие:** вторая запись затирает первую: в текущей публикации остаётся только одно из двух одобренных изменений, а версий с номером 6 может оказаться две. Если оба предложения меняют одно поле, сервер не замечает конфликта и публикует оба. Никто не получает сообщения об ошибке.

**Граница / точка входа:** TB-01 - два одновременных апрува (O5) предложений одной пары.

**Связанные SR:** [SR-06](security-requirements.md#sr-06-публикуется-только-бесконфликтный-и-допустимый-результат-целиком-или-никак).

**Приоритет:** высокий. Последствие - потребитель получает конфигурацию без одобренного изменения, и ошибку никто не замечает. Особых условий не нужно: несколько редакторов одной конфигурации - обычная работа, а два одновременных запроса может отправить и один пользователь.

### T-07. Затратный YAML останавливает сервис

**Ситуация:** редактор C отправляет предложение (O4) со специально составленным YAML. Например, якорь `a` ссылается 10 раз на якорь `b`, тот - 10 раз на `c`, и так далее: текст занимает меньше килобайта, а после раскрытия алиасов превращается в миллиард узлов. Другой вариант - вложенность в тысячи уровней. Сервер полностью разбирает документ и только потом проверяет ограничения из раздела 7 паспорта.

**Последствие:** разбор занимает всю память или время процессора, и сервер перестаёт отвечать остальным пользователям и потребителям. При рекурсивном разборе глубокая вложенность переполняет стек, а такую ошибку в .NET нельзя перехватить - процесс завершается целиком.

**Граница / точка входа:** TB-01 - тело запроса отправки предложения (O4).

**Связанные SR:** [SR-07](security-requirements.md#sr-07-недопустимое-предложение-отклоняется-и-не-нарушает-работу-сервиса).

**Приоритет:** высокий. Последствие - сервис недоступен всем, включая потребителей prod. Особых условий не нужно: достаточно прав редактора любой конфигурации и одного запроса, а примеры такого YAML общеизвестны.

### T-08. Сервисный клиент выходит за пределы своей пары

**Ситуация:** сервисному клиенту пары (C, dev) разрешено только получать её текущую конфигурацию (O10). Его учётные данные хранятся в приложении-потребителе, вне контроля команды. С ними - владельцем приложения или тем, к кому они утекли, - отправляется один из запросов:

- получение текущей конфигурации другой пары, например (C, prod) или (D, prod). Сервер проверяет только, что запрос пришёл от сервисного клиента, и не сверяет пару с его доступом;
- просмотр версий, предложений или истории (O1–O3), который предназначен людям. Сервер проверяет только, что учётные данные действительны.

**Последствие:** раскрываются рабочие настройки prod и чужих конфигураций, а во втором варианте - ещё и планируемые изменения и история пары.

**Граница / точка входа:** TB-02 - конфигурация и окружение в запросе текущей конфигурации (O10); запросы сервисного клиента к операциям просмотра (O1–O3).

**Связанные SR:** [SR-08](security-requirements.md#sr-08-сервисный-клиент-получает-только-текущую-конфигурацию-своей-пары).

**Приоритет:** средний. Последствие - только раскрытие: опубликованные настройки не меняются. Для сценария нужны учётные данные сервисного клиента: они есть только у приложения-потребителя, и постороннему их нужно сначала получить.

### T-09. Решение апрувера после исключения из списка

**Ситуация:** администратор исключил пользователя A из апруверов prod конфигурации C. После этого A со своими учётными данными одобряет или отклоняет предложение пары (C, prod). Сервер проверяет права не по текущему списку, а по сохранённому раньше: например, по ролям, записанным в учётные данные при входе A, или по списку на момент отправки предложения.

**Последствие:** удаление из списка не действует: в prod по-прежнему выпускает изменения человек, у которого право уже отозвали.

**Граница / точка входа:** TB-01 - апрув и отклонение (O5, O6) после изменения списка апруверов (O8).

**Связанные SR:** [SR-03](security-requirements.md#sr-03-решение-по-предложению-принимает-только-уполномоченный-для-окружения), [SR-09](security-requirements.md#sr-09-списки-апруверов-prod-меняет-только-администратор).

**Приоритет:** высокий. Последствие - администратор теряет контроль над тем, кто выпускает изменения в prod. Особых условий не нужно: сокращение списка апруверов - обычное действие администратора, а A достаточно своих учётных данных.

### T-10. Два корректных предложения вместе нарушают схему

**Ситуация:** схема C требует, чтобы `minPoolSize` был не больше `maxPoolSize`; в текущей публикации (C, prod) это 5 и 10. На рассмотрении два предложения с одной базовой версией: первое меняет `minPoolSize` на 8, второе - `maxPoolSize` на 6. Каждое по отдельности проходит проверку: 8 ≤ 10 и 5 ≤ 6. Поля разные, поэтому конфликта нет. После апрува первого предложения апрув второго (O5) проверяет схему только для изменяемого поля или для базовой версии, а не для всей итоговой конфигурации. Злоумышленник для этого не нужен.

**Последствие:** потребитель получает конфигурацию, которая нарушает схему: `minPoolSize` равен 8, а `maxPoolSize` - 6. Приложение может не запуститься или работать неправильно.

**Граница / точка входа:** TB-01 - апрув (O5) второго предложения.

**Связанные SR:** [SR-06](security-requirements.md#sr-06-публикуется-только-бесконфликтный-и-допустимый-результат-целиком-или-никак).

**Приоритет:** средний. Последствия тяжёлые: в prod попадает недопустимая конфигурация. Но нужно редкое сочетание: связь между полями в схеме и два предложения по этим полям на рассмотрении одновременно.

### T-11. Сервер, апрувер и потребитель по-разному понимают значение

**Ситуация:** редактор отправляет значение, которое разные правила YAML толкуют по-разному: `010` (по YAML 1.2 - 10, по YAML 1.1 - восьмеричное 8), `yes` (строка или `true`), `"60"` (строка или число), значение с явным тегом. Сервер проверяет его по одним правилам, апрувер читает текст предложения, а потребитель разбирает опубликованную конфигурацию своей библиотекой. Сервер принимает значение, если десериализует YAML в строки и затем сам приводит их к числам, или отдаёт потребителю исходный текст вместо заново собранного YAML.

**Последствие:** в prod попадает значение, которое не прошло бы проверку схемы или которое апрувер понял иначе. Рассмотрение формально пройдено, но одобрено не то, что применилось.

**Граница / точка входа:** TB-01 - значения `new` в отправке предложения (O4); TB-02 - выдача текущей конфигурации (O10).

**Связанные SR:** [SR-07](security-requirements.md#sr-07-недопустимое-предложение-отклоняется-и-не-нарушает-работу-сервиса), [SR-08](security-requirements.md#sr-08-сервисный-клиент-получает-только-текущую-конфигурацию-своей-пары).

**Приоритет:** средний. Последствие тяжёлое: обходятся и проверка схемы, и рассмотрение prod. Но нужно редкое условие: у потребителя библиотека с другими правилами YAML или ошибка в валидаторе сервера.

### T-12. Отзыв и апрув одного предложения одновременно

**Ситуация:** автор нашёл ошибку в своём предложении для пары (C, prod) и отзывает его (O11). В тот же момент апрувер prod C одобряет это предложение (O5). Оба запроса проверяют, что предложение в статусе `in_review`, до того как другой запрос что-то записал. Злоумышленник для этого не нужен.

**Последствие:** если выполняются оба запроса, изменение опубликовано, а предложение при этом числится отозванным, и история не совпадает с публикацией. Если апрув проверил статус до отзыва, а записал результат после, в prod уходит изменение, которое автор уже отменил из-за найденной ошибки.

**Граница / точка входа:** TB-01 - одновременные отзыв (O11) и апрув (O5) одного предложения.

**Связанные SR:** [SR-11](security-requirements.md#sr-11-отозвать-предложение-может-только-его-автор-пока-оно-на-рассмотрении), [SR-05](security-requirements.md#sr-05-отправленное-предложение-и-опубликованная-версия-не-меняются).

**Приоритет:** средний. Последствие тяжёлое: в prod попадает изменение, которое автор отменил. Но нужно совпадение во времени двух запросов разных людей по одному предложению.

## 5. Приоритетный набор

**Выбранный набор:** T-01, T-02, T-03, T-05, T-07.

Набор выбран из угроз высокого приоритета в два шага.

1. **Охват.** Для каждого свойства из [раздела 3](#3-значимые-объекты-и-свойства) берём хотя бы одну угрозу. Для доступа к данным, неизменности предложения и работы сервиса такая угроза одна - T-02, T-05 и T-07. Учётные данные и назначения вместе с историей покрывает T-01.
2. **Последствие.** Если на свойство приходится несколько угроз, выбираем ту, при которой в prod попадают непроверенные изменения или перестаёт работать сама проверка. Для учётных данных и назначений это T-01: она отключает все проверки прав сразу, а T-04 и T-09 затрагивают только список апруверов. Для текущей публикации это T-03: изменения уходят в prod без проверки, а при T-06 теряется изменение, которое уже одобрили.

T-04, T-06 и T-09 остаются угрозами высокого приоритета, но в набор не входят: нарушаемые ими свойства уже покрыты угрозами с более тяжёлыми последствиями. T-08, T-10, T-11 и T-12 имеют средний приоритет. Решения и будущие проверки для набора описаны в [проектных решениях](design-decisions.md).
