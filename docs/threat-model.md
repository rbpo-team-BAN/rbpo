# Модель угроз ConfigRelease

## Модель продукта

Компоненты и потоки — в [разделе 6 паспорта](../PROJECT.md#6-компоненты-и-внешние-взаимодействия), роли и назначения — в [разделе 3](../PROJECT.md#3-пользователи-и-доступные-действия), операции O1–O10 — в [требованиях безопасности](security-requirements.md#термины-в-критериях-приёмки).

**Что уже существует:** локальный ASP.NET Core API с `GET /health` и инструкция запуска. Этот endpoint не читает настройки и не выполняет предметные операции.

**Что пока планируется:** аутентификация пользователей и сервисных клиентов, проверка прав, обработка YAML, предложения изменений, апрув и отклонение, выдача публикаций, управление апруверами, SQLite и история. Угрозы ниже относятся к этой проектируемой части.

**Основные потоки:**

- редактор отправляет ID конфигурации и окружение, YAML с базовой версией и изменениями полей; API проверяет права и сохраняет предложение;
- редактор dev или апрувер prod отправляет ID предложения и решение; API проверяет сохранённые сведения, применяет изменения либо сохраняет отклонение;
- администратор отправляет изменение списка апруверов; API проверяет его назначение и сохраняет изменение с историей;
- сервисный клиент запрашивает текущую публикацию своей пары; API возвращает полную конфигурацию;
- API читает и записывает предложения, версии, права, текущие публикации, отметки полей и историю в SQLite.

**Существенные допущения:**

- запуск локальный, один экземпляр API и одна база; публичное размещение и несколько экземпляров пока не проектируются;
- клиенты не имеют прямого доступа к базе; API принимает решения по серверным назначениям и сохранённому состоянию, а не по заявлениям клиента;
- команда управляет компьютером, начальными данными, схемами и учётными данными. Если кто-то захватит ОС или получит доступ к файлу базы, модель от этого не защищает;
- администратор доверен управлять апруверами и может добавить себя. Это допустимое изменение прав; оно не отменяет запрет самоапрува prod;
- используются учебные данные;
- контроль корректности YAML не гарантирует доступность при неограниченном потоке запросов. Защита от сетевого DDoS и работа приложения-потребителя вне границ продукта.

## Границы доверия

| Граница | Что пересекает | Почему требуется проверка |
| --- | --- | --- |
| TB-01. Пользователь → API | Учётные данные, ID, окружение, предложение и решение, изменение апруверов | Клиент может изменить запрос напрямую, назвать чужой объект или исполнителя; наличие учётных данных не означает право на любое действие |
| TB-02. Сервисный клиент → API | Учётные данные и запрос текущей публикации | Клиенту разрешено чтение только одной пары; его учётные данные могут утечь в приложении-потребителе |
| TB-03. YAML → предметные данные API | Текст, ключи, теги, типы и значения | Синтаксически допустимый YAML может нарушать схему, менять типы или создавать лишнюю работу парсеру |
| TB-04. Компьютер и начальная настройка → доверенное состояние | Пользователи, назначения, схемы, учётные данные, файл базы | Их происхождение должно контролироваться командой; настройки нельзя принимать из обычного клиентского запроса |

SQLite — часть продукта, поэтому связь API с базой мы не считаем отдельной границей. Данным в базе мы доверяем, пока доступ к компьютеру и файлу базы есть только у команды. Если кто-то изменит файл напрямую, проверки API это не остановят.

## Значимые объекты и свойства

Объекты и последствия нарушения описаны в [разделе 5 паспорта](../PROJECT.md#5-значимые-данные-и-другие-объекты).

- **Настройки и предложения:** доступны только по назначениям; сохранённое предложение и опубликованная версия не меняются.
- **Текущая публикация и отметки полей:** соответствуют применённым предложениям; чужие или потерянные изменения не доходят до потребителя.
- **Учётные данные и права:** субъект определяется сервером; решение принимается по текущим назначениям и окружению.
- **История:** исполнитель достоверен, успешное изменение согласовано с записью, прежние записи нельзя переписать через API.
- **Работа сервиса:** недопустимое предложение отклоняется без аварийного завершения; после отказа разрешённые операции продолжают работать.

## Угрозы

В записях используются C — конфигурация, E — окружение, пара (C, E) — настройки C в E.

Шкала приоритета — высокий / средний. Высокий: обычным запросом к API можно прочитать чужие настройки, получить в prod не то, что одобрили, или остановить сервис, и в нашей архитектуре такую ошибку легко допустить. Средний: последствия есть, но для сценария нужны особые условия или ошибку легко заметить при первой проверке.

### T-01. Подмена исполнителя через поле запроса

**Ситуация:** пользователь A передаёт в теле, параметре или заголовке запроса имя пользователя B с большими правами. Сервер верит этому полю, когда проверяет права и записывает автора предложения или исполнителя в историю.

**Последствие:** действие выполняется с правами B. Запрет самоапрува перестаёт работать, а в истории записан не тот исполнитель.

**Граница / точка входа:** TB-01; сведения об исполнителе в HTTP-запросе.

**Связанные SR:** [SR-01](security-requirements.md#sr-01-действие-выполняется-от-имени-аутентифицированного-пользователя), [SR-10](security-requirements.md#sr-10-действия-прослеживаются-история-не-стирается).

**Приоритет:** средний — последствия тяжёлые: ошибка обходит все проверки ролей. Но для этого разработчик должен специально брать исполнителя из запроса. Обычно пользователя определяют по учётным данным, и ошибку видно при первом тесте с чужим именем в запросе.

### T-02. Доступ к чужому объекту по ID

**Ситуация:** редактор конфигурации C подставляет в запрос ID версии или предложения конфигурации D. Сервер проверяет права по C из адреса запроса и загружает объект по ID, не сверяя, к какой паре он относится.

**Последствие:** редактор читает чужие настройки и историю или принимает решение по чужому предложению.

**Граница / точка входа:** TB-01; ID объекта, конфигурация и окружение в параметрах запроса.

**Связанные SR:** [SR-02](security-requirements.md#sr-02-данные-конфигурации-доступны-только-по-назначениям), [SR-03](security-requirements.md#sr-03-решение-по-предложению-принимает-только-уполномоченный-для-окружения).

**Приоритет:** высокий — достаточно поменять один параметр обычного запроса; затрагивает и чтение, и публикацию.

### T-03. Самоапрув в prod

**Ситуация:** пользователь — редактор и апрувер prod одной конфигурации. Он отправляет предложение в prod и сам вызывает его апрув (O5) напрямую через API.

**Последствие:** его изменения уходят в prod без проверки другим человеком.

**Граница / точка входа:** TB-01; O5 и ID предложения.

**Связанные SR:** [SR-04](security-requirements.md#sr-04-нельзя-одобрить-собственное-предложение-в-prod).

**Приоритет:** высокий — совмещать роли разрешено, это обычная ситуация. Одна пропущенная проверка автора отменяет рассмотрение prod.

### T-04. Изменение списка апруверов без прав администратора

**Ситуация:** обычный пользователь напрямую вызывает изменение списка апруверов (O8) и добавляет себя или сообщника в апруверы prod.

**Последствие:** решения в prod принимает тот, кому администратор этого не разрешал.

**Граница / точка входа:** TB-01; O7–O9.

**Связанные SR:** [SR-09](security-requirements.md#sr-09-списки-апруверов-prod-меняет-только-администратор).

**Приоритет:** средний — последствия тяжёлые, но это одна проверка роли администратора на трёх операциях. Если её нет, это сразу видно в тесте под обычным пользователем.

### T-05. Подмена окружения в запросе апрува

**Ситуация:** автор отправил предложение в dev. В запросе апрува он передаёт окружение prod, и сервер берёт окружение из запроса вместо сохранённого предложения.

**Последствие:** изменения, которые автор одобрил сам по правилам dev, публикуются в prod без рассмотрения.

**Граница / точка входа:** TB-01; дополнительные поля в запросе решения (O5).

**Связанные SR:** [SR-05](security-requirements.md#sr-05-отправленное-предложение-и-опубликованная-версия-не-меняются).

**Приоритет:** средний — для этого обработчик апрува должен читать окружение из запроса. Операций изменения сохранённого предложения в API нет.

### T-06. Потеря изменений при одновременных апрувах

**Ситуация:** два апрувера одновременно одобряют предложения одной пары, которые меняют одно и то же поле. Оба читают одно и то же состояние, и второй при записи затирает изменение первого.

**Последствие:** потребитель получает конфигурацию без одного из одобренных изменений; могут появиться две версии с одним номером.

**Граница / точка входа:** TB-01; O5, чтение текущей публикации и запись версии в SQLite.

**Связанные SR:** [SR-06](security-requirements.md#sr-06-публикуется-только-бесконфликтный-и-допустимый-результат-целиком-или-никак).

**Приоритет:** высокий — несколько редакторов одной конфигурации — обычная работа. Ошибка тихая: никто не получает сообщения о конфликте.

### T-07. Затратный YAML останавливает сервис

**Ситуация:** редактор с правом O4 отправляет YAML с глубокой вложенностью, алиасами и повторяющимися ключами. Сервер строит объекты до проверки ограничений и тратит на разбор память и время.

**Последствие:** сервер падает или перестаёт отвечать остальным пользователям и потребителям.

**Граница / точка входа:** TB-01, TB-03; YAML-тело O4 и парсер.

**Связанные SR:** [SR-07](security-requirements.md#sr-07-недопустимое-предложение-отклоняется-и-не-нарушает-работу-сервиса).

**Приоритет:** высокий — это основной канал внешнего ввода. Файл присылает пользователь с правом редактора, но его содержимое всё равно нужно проверять.

### T-08. Утёкший токен потребителя читает чужое окружение

**Ситуация:** токен сервисного клиента пары (C, dev) утёк из приложения-потребителя. С ним запрашивают текущую конфигурацию (C, prod). Сервер проверяет только, что запрос пришёл от сервисного клиента, и не сверяет пару.

**Последствие:** раскрываются рабочие настройки prod.

**Граница / точка входа:** TB-02; O10 и пара в запросе.

**Связанные SR:** [SR-08](security-requirements.md#sr-08-сервисный-клиент-получает-только-текущую-конфигурацию-своей-пары).

**Приоритет:** средний — нужен утёкший токен, а последствие — только раскрытие настроек.

### T-09. Решение апрувера после исключения из списка

**Ситуация:** администратор исключил пользователя A из апруверов prod конфигурации C. A со своими прежними учётными данными вызывает апрув предложения (C, prod). Сервер проверяет права по списку, запомненному при входе или при отправке предложения.

**Последствие:** в prod выпускает изменения человек, у которого право уже отозвали.

**Граница / точка входа:** TB-01; O5 и O6, текущий список апруверов в базе.

**Связанные SR:** [SR-03](security-requirements.md#sr-03-решение-по-предложению-принимает-только-уполномоченный-для-окружения), [SR-09](security-requirements.md#sr-09-списки-апруверов-prod-меняет-только-администратор).

**Приоритет:** высокий — ошибку легко пропустить: при обычной проверке прав всё работает, сбой виден только после изменения списка.

### T-10. Два корректных предложения вместе нарушают схему

**Ситуация:** схема требует `min <= max`. Предложение A меняет `min`, предложение B меняет `max`. Каждое по отдельности проходит проверку, поля разные, конфликта по отметкам нет, и сервер применяет оба.

**Последствие:** потребитель получает конфигурацию, которая нарушает схему.

**Граница / точка входа:** TB-01; O5 и проверка итоговой конфигурации.

**Связанные SR:** [SR-06](security-requirements.md#sr-06-публикуется-только-бесконфликтный-и-допустимый-результат-целиком-или-никак).

**Приоритет:** средний — нужна связь полей в схеме и два предложения подряд. Угрозу нашли при разборе решения D-02 (пограничный случай в [D-02](design-decisions.md#d-02-команды-меняют-состояние-и-историю-атомарно)).

### T-11. Сервер, апрувер и потребитель по-разному понимают значение

**Ситуация:** редактор отправляет значение, которое разные правила YAML толкуют по-разному: `010` (по YAML 1.2 — 10, по YAML 1.1 — восьмеричное 8), `yes` (строка или `true`), `"60"` (строка или число), значение с явным тегом. Сервер проверяет его по одним правилам, апрувер читает текст предложения, а потребитель разбирает опубликованную конфигурацию своей библиотекой. Сервер принимает значение, если десериализует YAML в строки и затем сам приводит их к числам, или отдаёт потребителю исходный текст вместо заново собранного YAML.

**Последствие:** в prod попадает значение, которое не прошло бы проверку схемы или которое апрувер понял иначе. Рассмотрение формально пройдено, но одобрено не то, что применилось.

**Граница / точка входа:** TB-03; значения `new` в O4, выдача конфигурации в O10.

**Связанные SR:** [SR-07](security-requirements.md#sr-07-недопустимое-предложение-отклоняется-и-не-нарушает-работу-сервиса), [SR-08](security-requirements.md#sr-08-сервисный-клиент-получает-только-текущую-конфигурацию-своей-пары).

**Приоритет:** средний — нужна библиотека с другими правилами у потребителя или ошибка в валидаторе сервера, но последствие обходит и проверку схемы, и рассмотрение prod.

## Приоритетный набор

**Выбранный набор:** T-02, T-03, T-06, T-07, T-09. Это угрозы высокого приоритета: при каждой из них обычным запросом можно прочитать чужие настройки, получить в prod не то, что одобрили, или остановить сервис. Набор затрагивает все три решения: D-01 (T-02, T-03, T-09), D-02 (T-06) и D-03 (T-07).

Остальные угрозы связаны с теми же решениями. Будущие проверки описаны в [проектных решениях](design-decisions.md), все цепочки T → SR → D → проверка собраны в [таблице связей](design-decisions.md#связи-t--sr--d--проверка).
